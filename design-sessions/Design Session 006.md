# Design Session 006 – Work Package Lifecycle

## Purpose

A Work Package is the primary object exchanged between engineering stages.

It is designed primarily for AI agents.

Human-readable summaries are produced by higher-level agents such as the Orchestrator when needed.

The Work Package should be deterministic and machine-first.

## High-Level Structure

The Work Package should contain structured information rather than long narrative text.

The discussion identified the following conceptual sections:

- Summary
- Verification Guide
- Claims
- Evidence
- Worker Notes
- Risks (when applicable)

The exact schema remains intentionally undefined and will be designed later.

## Verification Guide

The Work Package should tell downstream stages how to verify the implementation.

Examples include:

- API endpoint
- Expected status codes
- Expected responses
- Primary verification steps

The goal is to reduce ambiguity for Reviewer and QA.

## Machine-First Design

The Work Package is optimized for AI consumption.

Reviewers, QA, Coordinators, and Orchestrators consume the structured data directly.

Humans normally interact with summaries generated by higher-level agents rather than reading raw Work Packages.

## Task and Revisions

A Task has one identity.

The Task evolves through Revisions.

Example:

Task

Revision 1

Revision 2

Revision 3

History is preserved.

The Task identity never changes.

## Revision Model

Each Revision stores only the changes introduced in that Revision.

Repeated information should not be duplicated.

AI Engineering OS reconstructs the latest Task state by combining all Revisions.

This minimizes duplication while preserving history.

## Ownership

Workers create new Revisions.

Reviewers never modify Worker Revisions.

Reviewers only produce review decisions.

If work is rejected, the Coordinator routes the Task back to the Worker.

The Worker produces the next Revision.

At any point in time only one Revision is active.

## Core Principle

History is never rewritten.

Every Revision becomes part of the permanent engineering history.

The latest Task state is reconstructed from Revision history rather than replacing previous work.
