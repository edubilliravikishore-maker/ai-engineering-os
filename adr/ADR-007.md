# ADR-007: The Four Blocked Conditions & Checkpoint 6 Preconditions

## Status

**Accepted — 2026-09-05.**

Records the four Builder rulings that discharge `BLOCKED_CONDITIONS` and unblock Checkpoint 6, prepared following the Checkpoint 6 planning review and before any Kernel code exists.

This ADR resolves four questions that four prior records deliberately refused to answer in passing: [Blueprint §14](../docs/02-implementation/Implementation-Blueprint.md) items 15, 16, 17 and 18, [ADR-004](ADR-004.md) 4.11 and *Questions Not Decided* item 3, [ADR-005](ADR-005.md) *Questions Not Decided* item 3, and [ADR-006](ADR-006.md) *Questions Not Decided* item 4.

**It supersedes nothing.** Every ruling here fills a stated gap. Two rulings *tighten* an existing invariant — the Actor capability requirement ([7.3](#73-reviewers-are-routed-by-capability-and-may-never-review-their-own-work)) and the QA-report selection the acceptance rules perform ([7.4](#74-qa-rounds-select-the-current-defect-position)) — and both are recorded as tightenings, not as corrections. No Design Session, ADR-001, ADR-002, ADR-003, ADR-004, ADR-005 or ADR-006 ruling is altered.

---

## Context

Checkpoints 1 through 5 are delivered, green and pushed. The OS can model its domain (CP2), evaluate rules (CP3), remember (CP4) and announce (CP5). It cannot yet *act*: the Kernel and the transactional Transition Runner are Checkpoint 6, and `core/` does not exist.

Checkpoint 6 is gated. The Foundation v1 Rule Coverage Gate ([ADR-004](ADR-004.md) 4.12, 4.13) forbids the Kernel operating against Foundation v1 while any of the 24 required transition conditions is unenforced. Of those 24, `BLOCKED_CONDITIONS` holds four — and unlike `PENDING_RULE_EXPANSION`, that set was defined precisely so that an unanswered *architectural* question could not hide inside a backlog:

| Condition | Why it could not be written |
| :--- | :--- |
| `ALL_IMPLEMENTATION_TASKS_ACCEPTED` | "Implementation task" is undefined across Design Sessions 001–009, ADR-003 and the Blueprint |
| `MANDATORY_EVIDENCE_PRESENT` | No Feature-level required evidence set exists anywhere; Design Session 005's standards are per-Worker-type |
| `REVIEWER_ASSIGNED` | **No domain concept exists.** `Task` carries no reviewer and no routing model is defined |
| `TASKS_INSTANTIATED` | Not a missing decision — Plan activation *performs* the instantiation (ADR-003 3.12), so the condition is meaningless until the Checkpoint 6 runner acts |

Three of the four therefore needed a Builder ruling. The fourth needed Checkpoint 6 machinery, and is recorded here only so the gate's arithmetic is unambiguous ([7.5](#75-tasks_instantiated-is-discharged-by-machinery-not-by-ruling)).

A fifth question sits alongside them. `ZERO_UNRESOLVED_IN_SCOPE_DEFECTS` **is** implemented — but its rule carries an explicit, deliberate hole. QA Reports are immutable (Blueprint §7.1), repeat QA is normal, and the §5.1 `IN_VALIDATION -> IN_PROGRESS` rework loop produces more reports. A defect recorded `OPEN` in a superseded report stays `OPEN` in that record forever. Evaluating every historical report as live makes any Feature that ever failed QA permanently unacceptable and renders the rework loop unreachable. Nothing in the architecture identified which report states a Feature's **current** defect position, so `QAInScopeZeroDefectsRule` invents no selection at all and records the consequence in its own docstring.

**Both obvious answers were closed off on purpose.** [ADR-005](ADR-005.md) 5.9 forbids using database persistence-metadata timestamps for ordering, filtering, or authoritative QA-result selection. [ADR-006](ADR-006.md) 6.1 confirms the event `sequence_number` is an append-order key and not a result selector. Whatever answers item 18 therefore has to be designed, which was the point of closing them.

The Builder ruled on all four questions on 2026-09-05. This record states those rulings, and states plainly what each one costs.

### 7.1 An Implementation Task Is Any Task Whose Capability Is Not QA

**Existing architectural requirement.** Blueprint §5.1 gates `IN_PROGRESS -> IN_VALIDATION` on `ALL_IMPLEMENTATION_TASKS_ACCEPTED`. Every `Task` already carries exactly one `CapabilityType` — `BACKEND`, `FRONTEND` or `QA` — and capability already governs Worker assignment (§5.2 `READY -> ASSIGNED`).

**Clarification.** An **implementation task** is a `Task` recorded against the Feature whose `capability` is **not** `QA`. `ALL_IMPLEMENTATION_TASKS_ACCEPTED` holds when every such Task is `ACCEPTED`.

This is a **ruling, not an inference.** Blueprint §14 item 15 was right that *deriving* the definition from `capability != QA` inside an implementation would be inventing architecture; the same predicate stated deliberately by the Builder, with its rationale and its cost recorded, is not. What was forbidden was the silence, not the predicate.

**Why QA-capability Tasks are excluded.** A QA-capability Task on a Feature exists to verify that Feature. Requiring it to be `ACCEPTED` before the Feature may enter `IN_VALIDATION` makes validation wait on work whose purpose is to perform validation. The condition would be unsatisfiable for any Feature that carries one, and the Foundation v1 vertical slice would not complete.

**The distinction that makes this safe.** Foundation v1 declares two separate conditions, and this ruling is what separates them:

| Condition | Transition | Scope after this ruling |
| :--- | :--- | :--- |
| `ALL_IMPLEMENTATION_TASKS_ACCEPTED` | Feature `IN_PROGRESS -> IN_VALIDATION` | Non-QA Tasks only |
| `ALL_TASKS_ACCEPTED` | Feature `IN_VALIDATION -> ACCEPTED` | **Every** Task, QA included |

Nothing escapes acceptance. A QA-capability Task is not exempt from ever being accepted — it is exempt from blocking the gate that lets QA begin. The two conditions differ by exactly the QA Tasks, which is why both exist.

**No new field.** The predicate reads a value the `Task` aggregate already holds. No column, no migration, no per-Task flag.

**The rejected alternative, and why.** A per-Task boolean marking work as "implementation" or not was considered and refused. It would have permitted genuinely non-blocking work — a spike, a research task — to be excluded from the gate. It would also have made the gate optional: a gate with a per-record off-switch is defeated by the first mislabelled record, and this gate exists precisely because ADR-003 and ADR-004 were written to stop conditions being settled quietly. Trading a small loss of expressiveness for a gate that cannot be dodged is the intended trade.

**Explicit deferral.** Foundation v1 has no concept of non-blocking work attached to a Feature. If that need proves real, the answer is a **new `CapabilityType`** added deliberately, with its own ruling and its own entry in `MANDATORY_SYSTEM_EVIDENCE` — not a flag on `Task`. Recorded as owed, not as planned.

### 7.2 Code, Tests And Reasoning Are The Feature-Level Evidence Set

**Existing architectural requirement.** Blueprint §5.1 gates `IN_VALIDATION -> ACCEPTED` on `MANDATORY_EVIDENCE_PRESENT`, and Design Session 009 requires mandatory QA evidence present at Feature Acceptance. Six `EvidenceType` values already exist. `MANDATORY_SYSTEM_EVIDENCE` already defines a **per-capability, per-Task** standard for Task submission (`BACKEND`: `GIT_DIFF`, `TEST_OUTPUT`, `API_RESPONSE`), and a capability absent from that table fails closed.

**Clarification.** The Feature-level mandatory evidence set is:

| Evidence type | Plain meaning |
| :--- | :--- |
| `GIT_DIFF` | Something was actually built |
| `TEST_OUTPUT` | Something was actually tested |
| `REASONING` | Somebody recorded what was done and why |

`MANDATORY_EVIDENCE_PRESENT` holds when **at least one** `EvidenceRecord` of each of those three types exists within the Feature's evidence closure — the Evidence attached to the Work Packages of the Feature's Tasks' Revisions, together with the Evidence attached to the Feature's **current-round** QA Reports ([7.4](#74-qa-rounds-select-the-current-defect-position)).

**This is a Feature-level floor, not a second per-Task standard.** It does not modify `MANDATORY_SYSTEM_EVIDENCE`, does not add a per-capability entry, and does not require every Task to carry all three. It asks one question of the Feature as a whole, once, at acceptance.

**Why these three and not the other three.** `API_RESPONSE` and `DB_VERIFICATION` are not true of every Feature — a purely front-end Feature has no endpoint to call and no row to verify. Requiring them at Feature level would force Workers to attach evidence that does not exist, which produces fabricated records, which is worse than requiring nothing. `BUILD_LOG` is per-capability infrastructure, already available where it applies. The three chosen are true of every Feature that was genuinely built.

**Why `REASONING` is in the set — the Builder's ruling.** The Builder holds the Orchestrator position and reads this record. Code and tests state *what* happened; six months later the question is *why*. The reasoning record is the Builder's own instrument and is therefore mandatory, not optional.

**The requirement on the author of a `REASONING` record** is that it be written in **plain English, carrying the technical detail a reader needs to understand the decision** — not a restatement of the diff, and not jargon that assumes the reader was present. This is recorded as a stated standard on the author.

**What the OS actually enforces, stated without overclaim.** The OS checks that a `REASONING` record **exists** and is non-empty, and that its checksum matches its content. **It does not and cannot check that the reasoning is good, honest, or even relevant.** The plain-English standard above is a Builder standard enforced by the Builder at review, not a machine-checked invariant. Recording it as a rule the system enforces would be a false guarantee, and the known failure mode — a required prose field degenerating into box-ticking — is not prevented by this decision. It is accepted with eyes open.

**Explicit deferral.** No minimum length, no structure, no template and no quality heuristic is defined for `REASONING` in Foundation v1. No per-capability Feature-level variation exists. Adding a fourth required type later is straightforward; **removing one is not**, because Features accepted under the earlier set will not carry it — which is why the set is kept to the three that are always true.

### 7.3 Reviewers Are Routed By Capability And May Never Review Their Own Work

**Existing architectural requirement.** Blueprint §5.2 gates Task `SUBMITTED -> IN_REVIEW` on `REVIEWER_ASSIGNED` and describes automatic routing to an assigned Reviewer. [ADR-001](ADR-001.md) states the principle this condition serves: **work is never completed by the agent that performs it.** `Actor` already carries `role`, `is_active` and `capabilities`; `ActorRole.REVIEWER` already exists.

**Clarification.** Three parts.

**(a) The `Task` aggregate gains a reviewer.** `Task.reviewer_id: ActorId | None`, recorded at the point of routing, null before it. Every option considered required somewhere to hold the answer; this is the least of them.

**(b) Eligibility.** An Actor may be routed a Task for review when **all** of the following hold. Failing any one, the transition is refused:

1. `role is ActorRole.REVIEWER`
2. `is_active is True`
3. the Actor's `capabilities` contain the Task's `capability`
4. the Actor is **not** the Task's assigned Worker, and **not** the author of any Revision of that Task

Condition 4 is ADR-001 made enforceable. It is the part of this ruling that matters most, and it holds from the first day the OS runs — not from the day a second Reviewer is registered.

**(c) Routing.** The Kernel computes the eligible set at `SUBMITTED -> IN_REVIEW` and selects deterministically, **ascending by `ActorId`**. An empty eligible set **refuses the transition**, consistent with the fail-closed stance of `SystemEvidenceRequiredRule`: the OS never invents a reviewer, never routes to the Builder as a fallback, and never lets an unreviewed Task advance.

**A tightening, recorded as such.** `Actor` currently requires at least one declared capability of `WORKER` only. Part (b) condition 3 makes the same requirement of `REVIEWER`: a Reviewer with no declared capability is eligible for nothing, so permitting one creates an Actor that can never be routed anything. The `Actor` validator is extended to require at least one capability for `REVIEWER` as well as `WORKER`. This tightens the invariant in Blueprint §4.1 #9; it removes no existing capability and changes no other role.

**Why routing, when there is exactly one Reviewer today.** With a single registered Reviewer this ruling behaves identically to "the Builder reviews everything" — every submitted Task lands in the same place. The difference is that no person is written into the architecture. Naming the Builder as the reviewer would have cost nothing today and required a redesign the day a second Reviewer exists. The cost of routing is one field and one selection step, and every rejected option needed the field anyway.

**Explicit deferral.** Foundation v1 does **not** implement load balancing, reviewer workload accounting, round-robin, reviewer preference, delegation, reassignment of an already-routed Task, escalation on reviewer inactivity, or any reviewer queue. Ascending `ActorId` is a deterministic tie-break, not a fair one: with several eligible Reviewers, one receives everything. That is acceptable while the eligible set has one member and is **recorded as owed** the moment it does not. No `reviewers` table, no routing policy object and no assignment history is created.

### 7.4 QA Rounds Select The Current Defect Position

**Existing architectural requirement.** QA Reports are immutable (Blueprint §7.1). The §5.1 `IN_VALIDATION -> IN_PROGRESS` rework loop is an approved transition and produces further reports. [ADR-005](ADR-005.md) 5.9 forbids database persistence-metadata timestamps as an authoritative QA-result selector. [ADR-006](ADR-006.md) 6.1 confirms `sequence_number` orders appended events and selects nothing.

**Clarification.** The Feature carries a **QA round**, and the round is what selects the current defect position.

1. `Feature.qa_round: int`, **starting at 1** when the Feature is created.
2. The Kernel increments it on exactly one transition: Feature `IN_VALIDATION -> IN_PROGRESS`, the rework loop. **One round is one build-and-check cycle**: the build, its Task-level QA, and the Feature-level validation that follows it all carry the same number.
3. `QAReport.qa_round: int`, **stamped by the Kernel from the Feature's current value at the moment the report is recorded** — never supplied by the reporting Actor, never derived from a clock.
4. `ZERO_UNRESOLVED_IN_SCOPE_DEFECTS` and `QA_FINAL_PASS_RECORDED` consider **only** reports whose `qa_round` equals the Feature's current `qa_round`.

Earlier rounds are never deleted, never edited and never re-evaluated as live. They remain exactly what they are: the permanent record that round 1 found two defects.

**Why the increment is on the rework loop and not on entry to `IN_VALIDATION`.** Task-level QA (Task `IN_QA -> ACCEPTED`) happens while the Feature is still `IN_PROGRESS`. Incrementing on entry to `IN_VALIDATION` would leave that Task-level QA stamped with the previous round and silently excluded from the validation it belongs to. Incrementing when the Feature is sent back for rework makes the boundary fall where the work actually restarts, so a cycle's Task-level QA and its Feature-level validation always share a number.

**Why the round is stamped at recording, not at authoring.** A report written during round 1 but submitted after rework has begun must remain a round 1 report. Stamping at the moment of recording, from the Feature's own field, makes that automatic. The mechanism has no dependence on when anybody wrote anything.

**Why a round and not a supersession pointer or a reported-at time.** A reported-at timestamp supplied by the QA Actor reintroduces exactly the trust ADR-005 5.9 removed — an external clock deciding an architectural question, with ties unresolvable. A supersession pointer (report *n* names the report it replaces) is explicit and clock-free, but it is a chain: one report recorded without its pointer yields two live heads and no defined way to choose, so the OS would have to police chain integrity as a separate invariant. The round number is owned by the Kernel, set by a transition the Kernel already performs, and cannot fork. It also makes the system **state** the current position rather than infer it, which is the difference between this and the two pre-closed answers.

**Per-defect resolution was rejected.** Tracking each defect and marking it resolved individually gives the most precise picture, but defect status would then change over time — reopening the immutability of QA Reports settled in Blueprint §7.1 and relied on by ADR-005 5.8. A ruling that unsettles a foundation to gain precision at one gate is not worth it.

**What this changes in already-shipped code, stated plainly.** `QAInScopeZeroDefectsRule` today performs **no** selection and records that fact in its docstring, deferring to the caller. After this ruling **the round filter is performed by the rule, not by the context loader.** The rule's original reasoning — that preferring one report over another would be inventing QA workflow semantics it does not own — was correct while no selector existed. One now exists, it is a domain field requiring no lookup, and leaving the filter to the loader would leave enforcement outside the enforcement layer, trusting every caller to get it right. `RuleFact.QA_REPORTS` continues to mean *every* report for the Feature; the rule narrows them. The docstring is corrected as part of Checkpoint 6.

**Explicit deferral.** No round is exposed as a user-facing "attempt number", no per-round summary or comparison is produced, no limit on rounds is imposed, and no round appears in any event payload beyond what the existing envelope carries. Reports from earlier rounds are readable history and nothing in Foundation v1 queries them.

### 7.5 `TASKS_INSTANTIATED` Is Discharged By Machinery, Not By Ruling

**Existing architectural requirement.** [ADR-003](ADR-003.md) 3.12 states that Plan activation *performs* Task instantiation. [ADR-004](ADR-004.md) 4.11 classified `TASKS_INSTANTIATED` as blocked on that basis — evaluating it before the Checkpoint 6 runner acts is meaningless, not undecided.

**Clarification.** No Builder ruling is owed. The condition is discharged by the Checkpoint 6 Transition Runner, which instantiates the Tasks within the Feature `PLANNED -> IN_PROGRESS` transaction and can then assert the outcome it has just produced. It is recorded here so the gate arithmetic is explicit: **three of the four `BLOCKED_CONDITIONS` are answered by 7.1 to 7.3; the fourth is answered by building Checkpoint 6.**

**Explicit deferral.** None. The condition leaves `BLOCKED_CONDITIONS` when the runner exists, not before.

### 7.6 Reaffirmed, Not Newly Decided

- **ADR-001 stands unchanged.** 7.3(b)(4) enforces it; it does not restate or extend it.
- **QA Report immutability stands unchanged** (Blueprint §7.1, ADR-005 5.8). 7.4 adds a stamped field to a new report; it edits none.
- **ADR-005 5.9 and ADR-006 6.1 stand unchanged and are reinforced.** Neither database timestamps nor `sequence_number` selects a QA result; 7.4 introduces a selector that is neither.
- **`MANDATORY_SYSTEM_EVIDENCE` stands unchanged.** 7.2 is a Feature-level floor and adds no per-capability entry. `FRONTEND` and `QA` still have no per-Task standard and still fail closed.
- **The `CapabilityType` vocabulary is unchanged.** No `RESEARCH` or equivalent is added; 7.1 records it as the shape of a future ruling only.
- **The `EvidenceType` vocabulary is unchanged.** 7.2 selects three of the existing six.
- **No new runtime dependency**, no new table, and no change to the event vocabulary or channel.

## Consequences

### Positive

- **`BLOCKED_CONDITIONS` drops from four to one**, and the remaining entry is machinery rather than an owed decision. The Checkpoint 6 gate becomes reachable.
- **The four questions are answered in a record written before the code**, holding the rhythm every checkpoint has followed: ADR first, implementation second.
- **ADR-001 becomes enforceable rather than aspirational.** Self-review is refused by the system from the first transition it runs.
- **`QAInScopeZeroDefectsRule`'s known hole closes.** The rework loop becomes reachable; a Feature that failed QA once can be accepted after it passes.
- **Two of the four rulings cost no schema change at all** (7.1, 7.2), because both read state the aggregates already hold.

### Trade-offs

- **7.1 makes every non-QA Task blocking.** A research or spike Task attached to a Feature must reach `ACCEPTED` before validation may begin. There is no exemption, deliberately, and until a new capability is ruled the only remedy is not to attach such work to the Feature.
- **7.2 requires prose the OS cannot judge.** `REASONING` is checked for existence and integrity only. The failure mode — a mandatory text field filled to satisfy the gate — is accepted, not prevented.
- **7.3's routing is deterministic but not fair.** With several eligible Reviewers, ascending `ActorId` sends everything to one. Harmless at one Reviewer; owed the moment there are two.
- **7.3 refuses transitions when no Reviewer is eligible.** A Feature can stall at `SUBMITTED` on an Actor-registry problem. Failing closed is the intended behaviour, and the refusal reason must name the cause precisely or the stall will be hard to diagnose.
- **7.4 adds a field to `Feature` and to `QAReport`**, and correctness depends on exactly one Kernel increment happening on exactly one transition. That is a small surface, but it is **not enforced by construction** — the same class of risk ADR-006 6.9 recorded for the notification emit, and it needs the same treatment: an explicit test that the rework loop increments and that no other transition does.
- **7.4 changes the behaviour of an already-shipped rule.** Existing tests that supply multiple QA Reports without a round will need the field; that churn is expected and is the price of closing the hole rather than working around it.

| Area | Change |
| :--- | :--- |
| `domain/task.py` | `Task.reviewer_id: ActorId \| None`, with the status-dependent invariant that a Task from `IN_REVIEW` onwards records one |
| `domain/actor.py` | Capability validator extended to `REVIEWER` |
| `domain/feature.py` | `Feature.qa_round: int`, default 1, never decreasing |
| `domain/qa.py` | `QAReport.qa_round: int` |

| `rules/` | New rules for `ALL_IMPLEMENTATION_TASKS_ACCEPTED`, `MANDATORY_EVIDENCE_PRESENT`, `REVIEWER_ASSIGNED`; round filter added to `QAInScopeZeroDefectsRule` and `QAFinalPassRecordedRule`; three conditions move from `BLOCKED_CONDITIONS` to `IMPLEMENTED_CONDITIONS` |

Required checks, in addition to the existing suite:

- The rework loop increments `qa_round` and **no other transition does**.
- A QA Report is always stamped from the Feature's current value at recording time.
- A Worker can never be routed their own Task for review, including via a Revision they authored.
- An empty eligible-Reviewer set refuses the transition with a reason naming the cause.
- The Rule Coverage Gate passes rather than being expected to fail.

## Foundation v1 Scope Boundary

**In scope, created by this record:** `Task.reviewer_id`; `Feature.qa_round`; `QAReport.qa_round`; the `REVIEWER` capability requirement; three new rules; a round filter on two existing rules; migration `0009`; reviewer routing and round management in the Checkpoint 6 Kernel.

**Out of scope, explicitly:** any reviewer queue, workload model, fairness policy, delegation or escalation; any per-Task non-blocking flag; any new `CapabilityType` or `EvidenceType`; any change to QA Report immutability; any per-defect resolution tracking; any quality assessment of `REASONING`; any round-aware reporting, history query or UI surface.

**The gate after this record:** of the 24 Foundation v1 required conditions, `TASKS_INSTANTIATED` alone remains in `BLOCKED_CONDITIONS`, and it leaves that set when the Checkpoint 6 Transition Runner exists. Checkpoint 6 may not operate against Foundation v1 until the gate passes.
