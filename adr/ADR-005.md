# ADR-005: Persistence Architecture & Checkpoint 4 Scope

## Status

**Accepted — 2026-09-02.**

Records the persistence architecture for Foundation v1 and the scope of Checkpoint 4, prepared following the Checkpoint 4 planning review and the reconciliation of the Builder decisions against the existing architecture.

This ADR is an implementation-foundation and clarification record for the persistence layer. **It does not replace, restate, or redesign the architecture.** It supersedes exactly one prior record: the Implementation Blueprint §14 item 1 *recommendation* on locking strategy (see [5.6](#56-concurrency--optimistic-locking)). It amends the Blueprint classification of `work_packages` in §7.1 ([5.8](#58-immutable-history-and-the-work-package-hybrid)) and the checkpoint ownership of the event and audit tables ([5.13](#513-events-and-transition-audit-deferred-to-checkpoint-5)). No Design Session, ADR-001, ADR-002, ADR-003, or ADR-004 ruling is altered.

---

## Context

Design Sessions 001–009 froze the architecture. [ADR-001](ADR-001.md) established independent verification. [ADR-002](ADR-002.md) established the technology foundation, named PostgreSQL as the authoritative system of record, and deliberately deferred the complete database schema to the implementation blueprint. [ADR-003](ADR-003.md) resolved the domain-model and lifecycle ambiguities discovered during Checkpoint 2. [ADR-004](ADR-004.md) established the Rule Engine and the scope of Checkpoint 3.

Checkpoint 2 implemented the pure domain layer (`domain/`) and the lifecycle state machines (`state/`). Checkpoint 3 implemented the Rule Engine (`rules/`) and proved it against six real OS rules. **All of it runs in memory.** Nothing the OS knows survives a process restart, and no component can supply a rule with facts, because there is nowhere to read facts from.

[ADR-004](ADR-004.md) 4.4 states the position explicitly: the **context loader** — the component that reads facts from persistence and assembles a `RuleContext` — "is **not** part of Checkpoint 3. It belongs to the Checkpoint 6 Kernel and is built on **Checkpoint 4 repositories**."

**Checkpoint 4 builds those repositories, and the schema beneath them.** It stores and retrieves. It evaluates no rule, validates no transition, and advances no state.

Turning the frozen domain model into relational tables surfaced a set of points where the authoritative documents were silent, underspecified, or internally inconsistent — the same class of problem [ADR-003](ADR-003.md) and [ADR-004](ADR-004.md) exist to record. This ADR records the Builder's resolution of them.

### 5.1 A Single `actors` Table

**Decision.** Actor identity is persisted in **one `actors` table**, with `role` as a column.

**No `coordinators` table and no Domain Registry persistence is created.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | The domain models a single `Actor` carrying `id`, `role`, `name`, `domain`, `is_active`, and `capabilities` (Blueprint §4.1 #9, ADR-003 3.9). Foundation v1 uses `Actor.is_active` only (ADR-003 3.10). **No `coordinators` or Domain Registry persistence may be created** until the Coordinator lifecycle is resolved (ADR-003 3.10, §14 item 7). |
| **Clarification** | Blueprint §7.1's `coordinators` and `workers` boxes are replaced by a single `actors` table. This is the only arrangement that persists the domain model as written while respecting ADR-003 3.10's constraint. |
| **Explicit deferral** | The Design Session 009 Coordinator lifecycle, the Domain Registry, and the Builder-approval registration workflow **remain deferred and are not implemented**. `actors` stores identity only; it maps no domain to any Coordinator. |

**Rationale.** Two role-specific tables would contradict the single `Actor` domain model, and one of them is explicitly forbidden. A role column expresses the same information without creating the registry the architecture has not yet designed.

**Affects.** Blueprint §7.1.

### 5.2 Child Tables When The OS Reasons About The Contents; JSONB When The Object Is Whole

**Decision.** A nested structure becomes a **child table** when the OS needs to query or reason about its contents. It is stored as **JSONB** when it is treated as a whole.

**Not every nested object becomes a table.**

*Child tables:* `qa_defects`, `task_dependencies`, `plan_task_definitions`, `decision_acknowledgements`.

*JSONB:* `Feature.requirements` / `in_scope` / `out_of_scope` / `acceptance_criteria`; `FeaturePlan.required_capabilities`; `TaskDefinition.depends_on`; `Actor.capabilities`; `WorkPackage.claims` / `verification_guide` / `worker_notes`; `EvidenceRecord.metadata`; `QAReport.results` / `tested_scope`; `Decision.alternatives_considered` / `affected_domains`.

| | |
| :--- | :--- |
| **Existing architectural requirement** | The OS enforces the **integrity of the relationship**, not the semantic correctness of the judgement behind it (ADR-003 3.11). `Feature.in_scope` / `out_of_scope` remain free text and **the OS performs no text matching against them** (ADR-003 3.11). `claim_type` is descriptive and **never feeds a deterministic OS rule** (ADR-003 3.7). Plan dependency validity is guaranteed at construction and classified `SATISFIED_BY_DOMAIN_INVARIANT` (ADR-004 4.11). Complexity must be earned (ADR-002). |
| **Clarification** | The criterion by which each nested structure is placed. Defect scope, Task dependencies, plan definition keys, and acknowledgements are reasoned about by the OS; claim text, verification guides, reviewer notes, test result lists, and the Feature scope lists are not. |
| **Explicit deferral** | None. |

**Rationale.** `QAInScopeZeroDefectsRule` resolves `Defect -> Task -> Feature` per defect, and `DependenciesAcceptedRule` inspects each dependency, so those relationships must be first-class rows. Nothing in the architecture inspects the inside of a claim or a verification guide, so making them tables would be unearned complexity. Acknowledgements are a child table for a separate reason recorded in [5.8](#58-immutable-history-and-the-work-package-hybrid): appending one to a JSONB array would require rewriting an immutable `decisions` row.

**Affects.** Blueprint §7.1.

### 5.3 The Database Is The Durable Source Of Truth

**Decision.** PostgreSQL holds the durable persisted state. **Domain objects are the behavioural representation loaded from that state.**

A repository that cannot reconstruct a valid domain object from a stored row **fails**. It never returns an invalid domain object, and it never silently repairs one.

| | |
| :--- | :--- |
| **Existing architectural requirement** | PostgreSQL is the single source of truth; all state changes are committed within atomic transactions (ADR-002, Blueprint §2.4). Invalid workflow states must not be creatable through normal OS interfaces (ADR-002, *Testing Principles*). Domain models are frozen and fully revalidated on construction (Blueprint §4.1, ADR-003). |
| **Clarification** | Reconstruction runs every domain validator. A stored row that no longer forms a valid domain object raises at load time. |
| **Explicit deferral** | None. |

**Rationale.** Silent repair would let an invalid state re-enter the system through the back door, which is precisely the failure mode ADR-002's testing principles require to be unreachable. Failing loudly turns a corrupt row into a visible defect rather than an invisible one.

**Affects.** Blueprint §2.4, §7.

### 5.4 Generic Base Repository Plus Domain-Specific Repositories

**Decision.** A **generic base repository** carries only genuinely reusable persistence mechanics. **Domain-specific repositories** own every query shaped by a domain question.

**A generic CRUD surface is not exposed merely because a generic base exists.** Bulk reads are permitted where a real use case requires them; generic bulk CRUD is not. Lazy or streaming retrieval may be used where genuinely needed and is not forced onto every query.

| | |
| :--- | :--- |
| **Existing architectural requirement** | `storage` owns "SQLAlchemy models, repositories, session management, and Alembic migrations" and **must not own domain logic** (Blueprint §3, §2.2). Complexity must be earned (ADR-002). |
| **Clarification** | The split between reusable mechanics and domain queries, and the prohibition on exposing generic operations by default. |
| **Explicit deferral** | None. |

**Rationale.** A generic CRUD surface invites callers to reach for operations the domain never sanctioned — and the first such operation would be a delete, which [5.7](#57-no-generic-delete-capability) forbids outright. Bulk reads are earned by a real consumer: the `referenced_tasks` fact of the approved seven-fact `RuleContext` (ADR-004 4.4) resolves a list of Task identifiers, and resolving them one at a time would be a query per dependency.

**Affects.** Blueprint §3, §11.

### 5.5 The Service/Use-Case Layer Owns The Transaction

**Decision.** The **service/use-case layer owns the transaction boundary**. Repositories perform persistence operations; they do **not** decide where a business transaction begins or ends.

**One session per service/use-case transaction.** Repositories use the session supplied to them by the transaction boundary. Reads use normal sessions and queries by default; an explicit transaction is used only where a consistent multi-read snapshot is genuinely required.

| | |
| :--- | :--- |
| **Existing architectural requirement** | `core` owns the transaction runner and enforcement pipeline (Blueprint §3, §7.2). `storage` owns the **Unit of Work** (Blueprint §2.2). All OS state transitions are protected by explicit PostgreSQL ACID transactions (Blueprint §7.2). |
| **Clarification** | Repositories never call `commit()` or `rollback()`, and never open their own session. |
| **Explicit deferral** | **The service/use-case layer itself is the Checkpoint 6 OS Kernel and is NOT built at Checkpoint 4.** Checkpoint 4 ships the session-scope mechanism only; the transaction-owning caller arrives at Checkpoint 6. |

**Rationale.** Keeping the transactional boundary in exactly one place is a direct consequence of the OS being the enforcement layer, and is the same reasoning ADR-004 4.6 used to keep mutation in exactly one place. A repository that committed would let a partially applied transition reach durable storage.

**Affects.** Blueprint §7.2, §11.

### 5.6 Concurrency — Optimistic Locking

**Decision.** Concurrent modification is detected by **optimistic locking**, never silently overwritten.

> **This supersedes the Implementation Blueprint §14 item 1 recommendation of `SELECT FOR UPDATE`.**

Optimistic-lock versions apply to **mutable-state tables only**: `actors`, `features`, `feature_plans`, `tasks`, and `work_packages`. Append-only tables carry no version, because a row that is never updated cannot lose an update race.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Blueprint §14 item 1 posed the question and **recommended** `SELECT FOR UPDATE` for v1. A recommendation is not a ruling; §14 records "genuine technical implementation questions for Foundation v1". |
| **Clarification** | The Builder rules for optimistic locking. §14 item 1 is thereby **RESOLVED**, and its recommendation is superseded. |
| **Explicit deferral** | None. |

**Rationale.** A lost update is an unverified change overwriting a verified one — the write-side form of the failure ADR-001 exists to prevent. Detection makes the conflict explicit and hands the decision to the caller rather than resolving it by arrival order.

**Consequence for the domain layer: none.** The domain models are frozen and carry no `version` field. The version is a property of the stored row, tracked inside the session and never exposed across the repository boundary ([5.11](#511-repositories-return-domain-objects-only)). **No Checkpoint 2 domain model is modified.**

**Affects.** Blueprint §7.2, §14 item 1.

### 5.7 No Generic Delete Capability

**Decision.** There is **no generic `repository.delete()`**. Removal semantics must be explicitly designed by the domain if they are ever needed.

Foreign keys use **`RESTRICT`**. There is **no automatic cascading deletion**. Referenced identifiers are stable, so there is **no `ON UPDATE CASCADE`**.

**No lifecycle state such as `ABANDONED`, `CANCELLED`, or `STOPPED` is introduced.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | History is additive and never overwritten or discarded (Design Session 006, Design Session 009, Blueprint §1.4, §7.1). **No** automatic migration, reassignment, or deletion of a superseded plan's Tasks may be implemented in any repository or migration (ADR-003 3.13). The Task lifecycle defines **no** terminal state for stopped work; that is deferred capability **D-6** (ADR-003, §14 item 11). |
| **Clarification** | The prohibition is structural: the capability does not exist to be called. `RESTRICT` is the belt-and-braces expression of the same rule at the schema level. |
| **Explicit deferral** | **D-6 remains deferred.** Checkpoint 4 creates no disposition record, no stop state, and no link between a superseded plan's Task and successor planned work. |

**Rationale.** A generic delete is the single operation most likely to destroy the audit history the entire architecture is built to preserve. Cascading deletion would compound it by removing records the caller never named.

**Affects.** Blueprint §7.1, §14 item 11.

### 5.8 Immutable History And The Work Package Hybrid

**Decision.** Records that are architecturally historical or immutable are persisted **append-only**. Current mutable state may be updated where the architecture already permits it.

**Append-only:** `task_revisions`, `evidence_records`, `qa_reports`, `qa_defects`, `review_decisions`, `decisions`, `decision_acknowledgements`.

**Mutable state:** `actors`, `features`, `feature_plans`, `tasks`.

**`work_packages` is a hybrid**, and Blueprint §7.1's placement of it under append-only history is **amended**:

- A `DRAFT` Work Package remains editable.
- `SUBMITTED` is persisted as the durable record.
- **Submitted content becomes immutable.**
- **The existing approved lifecycle transitions remain the sole authority for status changes.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | Rows in append-only tables are inserted, never updated; `task_revisions` carries no mutable status column (Blueprint §7.1, ADR-003 3.1). A submitted Work Package is immutable and no actor may edit it; fixes require a new Revision and a new Work Package (Blueprint §5.3, ADR-003 3.5). After `SUBMITTED`, Work Package state is an **OS projection** of the Task lifecycle, with initiator `OS` (ADR-003 3.5). QA Reports are immutable audit history (ADR-004 4.15). |
| **Clarification** | Blueprint §7.1 listed `work_packages` under append-only history, which contradicted the five-value status projection ADR-003 3.5 requires. The contradiction is resolved in favour of a hybrid: **content immutable after submission, status projected by the already-approved state machine.** |
| **Explicit deferral** | The **mechanism** of append-only enforcement is by construction, not by database trigger — see *Trade-offs*. |

**Rationale.** ADR-003 3.5 and Blueprint §7.1 could not both be satisfied as written. Preserving 3.5's single-authority projection matters more than the shelf the table sits on: reclassifying the table changes documentation, whereas removing the status projection would recreate the second authority model 3.5 exists to eliminate.

`decision_acknowledgements` is a child table for this same reason: appending an acknowledgement to a JSONB array would require rewriting an immutable `decisions` row.

**Affects.** Blueprint §7.1, §12.

### 5.9 Application-Generated Identity, Database-Generated Persistence Metadata

**Decision.** Identity is **application-generated**, as UUIDs. An entity's identity exists before persistence, so a service-owned transaction can connect several new domain objects to each other before any of them is written.

**Persistence timestamps are database-generated and are metadata only:**

- **Existing domain timestamps remain domain-owned.** `Feature.created_at` / `updated_at`, `Task.created_at` / `updated_at`, `TaskRevision.created_at`, `WorkPackage.submitted_at`, `EvidenceRecord.created_at`, `QAReport.created_at`, `Decision.created_at`, `ReviewDecision.created_at`, and `DecisionAcknowledgement.acknowledged_at` are produced by the domain and persisted exactly as the domain produced them.
- **Database-generated timestamps are separate persistence metadata columns.** They record when a row physically landed. They are distinct from every domain timestamp above.
- **They are not mapped into domain objects.** No mapper reads them; no domain model gains a field for them.
- **Repositories must not use them for ordering or filtering, and must never use them for authoritative QA-result selection.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | Every entity is identified by a UUID and the domain generates it (`new_id`, Blueprint §4.1). Domain models generate their own timestamps. The `RuleContext` contains **no clock**, and its absence is a determinism guarantee (ADR-004 4.4). The authoritative / current QA-result mechanism is **UNRESOLVED** and must not be invented — specifically **no recency ordering, sequence number, timestamp comparison, "latest" marker, or `current_report_id`** (ADR-004 4.15, §14 item 18). |
| **Clarification** | The two kinds of timestamp are separate and never meet. A signed record carries the time the domain recorded; the row separately carries the time it was stored. |
| **Explicit deferral** | The authoritative / current QA-result selection mechanism **remains UNRESOLVED**. Persistence metadata timestamps **do not** constitute it and may not be used to construct it. |

**Rationale.** Two clocks are safe only while they never meet. Letting the database overwrite a domain timestamp would return objects carrying values the domain never produced, contradicting [5.3](#53-the-database-is-the-durable-source-of-truth), and would make `Task.with_status(at=...)` untruthful. The explicit prohibition on ordering exists because a `row_created_at` column on `qa_reports` is exactly the shape of the mechanism ADR-004 4.15 forbids inventing; storing the fact is permitted, using it to select an authoritative QA result is not.

**Affects.** Blueprint §7, §14 item 18.

### 5.10 Migrations Grouped By Coherent Schema Change; Applied Migrations Immutable

**Decision.** Migrations are grouped by **coherent schema change**. **An applied migration is immutable.** A correction is expressed as a new migration, never as an edit to one already applied.

**Consequence:** `0001_baseline` is **not edited**. It has been applied wherever `tests/integration/test_migrations.py` has run. Checkpoint 4 adds new revisions after it.

| | |
| :--- | :--- |
| **Existing architectural requirement** | All schema changes must be versioned and executed **exclusively through Alembic migrations**; agents and Workers must never independently alter the OS database schema (ADR-002, *Database Rules*). History is additive (Blueprint §1.4). |
| **Clarification** | Grouping criterion, and the immutability of an applied migration. |
| **Explicit deferral** | None. |

**Rationale.** An edited migration means two databases claiming the same revision identifier with different schemas — a silent divergence, which is the persistence-layer form of the history rewriting the architecture forbids everywhere else.

**Affects.** Blueprint §15 Checkpoint 4.

### 5.11 Repositories Return Domain Objects Only

**Decision.** Repositories return **domain objects**. **ORM and database models never cross the repository boundary.**

The Rule Engine and every higher layer must never receive a SQLAlchemy model.

| | |
| :--- | :--- |
| **Existing architectural requirement** | `storage` isolates all SQLAlchemy and relational mapping details (Blueprint §11, *Directory Rationale*). `rules` must not own DB connection management and depends only on `domain` (Blueprint §3). A rule must not access PostgreSQL, SQLAlchemy, any database session, or any repository (ADR-004 4.4). Every `RuleContext` field is a frozen domain model or a tuple of them, immutable **in depth** (ADR-004 4.4). |
| **Clarification** | The boundary is structural and verified by architectural test, not by convention. |
| **Explicit deferral** | None. |

**Rationale.** A leaked ORM object carries a live session with it. Lazy loading would then fire at unpredictable moments — eventually inside a rule evaluation — silently destroying the reproducibility guarantee ADR-004 4.4 was written to protect, without any import of `storage` ever appearing in `rules`.

**Affects.** Blueprint §3, §11.

### 5.12 Persistence Exceptions Are Translated At The Repository Boundary

**Decision.** The repository **translates infrastructure and database errors into application-level persistence exceptions**: `NotFoundError`, `ConcurrencyConflictError`, `PersistenceError`. A missing record raises a specific `NotFoundError`.

**The repository reports the problem; the service/use-case layer decides the business response.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | Domain errors "intentionally carry no HTTP status codes, transport concerns, or **persistence concerns**" (`domain/errors.py`). Rejections carry stable machine-readable codes rather than free-form strings (ADR-004 4.5). |
| **Clarification** | Persistence exceptions form their own hierarchy in `storage`, **not** in `domain/errors.py`, whose recorded scope excludes them. They carry no HTTP status codes; the transport mapping belongs to Checkpoint 7. |
| **Explicit deferral** | None. |

**Rationale.** A raw `IntegrityError` leaking upward would make every caller depend on SQLAlchemy, defeating [5.11](#511-repositories-return-domain-objects-only) through the exception path rather than the return path.

**Affects.** Blueprint §3, §11.

### 5.13 Events And Transition Audit Deferred To Checkpoint 5

**Decision.** **`os_events` and `state_transitions_audit` are deferred to Checkpoint 5.** Checkpoint 4 creates neither table, neither model, nor an event repository.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Checkpoint 5 implements the event model, append-only event recording, and the PostgreSQL LISTEN/NOTIFY emitter and subscriber (Blueprint §15 Checkpoint 5). PostgreSQL is the durable event store; LISTEN/NOTIFY is only a wake-up mechanism (ADR-002). |
| **Clarification** | Blueprint §11 marked `storage/models/event.py` as **[PLANNED — CP4]** and §15 Checkpoint 4 listed an `EventRepository`, while §15 Checkpoint 5 claimed the same artefact. The conflict is resolved in favour of Checkpoint 5. **`state_transitions_audit`, which no checkpoint previously owned, is assigned to Checkpoint 5.** |
| **Explicit deferral** | The event model, the event store, the transition audit table, the notification bus, and the rejection audit record all belong to Checkpoint 5 and later. |

**Rationale.** The event tables exist to serve the event layer, and separating a table from the code that writes it across a checkpoint boundary leaves an unowned artefact — exactly the ambiguity that produced this conflict. Ordering is unaffected: Checkpoint 4 → Checkpoint 5 → Checkpoint 6 still delivers the audit machinery before the Kernel that needs it.

**Affects.** Blueprint §4.1 #10, §11, §15 Checkpoints 4 and 5.

### 5.14 Database Constraints And Indexes

**Decision.** Database constraints are used for **fundamental data integrity**: `NOT NULL`, foreign keys, `UNIQUE`, and appropriate `CHECK` constraints. **Business and state-machine rules remain in the domain.**

Indexes are **evidence-based** — each supports an actual repository query pattern. **No speculative indexes. No database views** unless a concrete requirement later justifies one.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Invalid workflow states must not be creatable through normal OS interfaces (ADR-002, *Testing Principles*). `storage` must not own domain logic (Blueprint §3). Complexity must be earned (ADR-002). Evidence must be durable, retrievable, and integrity-verifiable (Blueprint §4.1 #6). |
| **Clarification** | The line between the two: a constraint may mirror an invariant the domain already validates, but may not encode a lifecycle rule the state machine owns. |
| **Explicit deferral** | None. |

**Three consequences follow from applying this decision to the actual schema, and are recorded here explicitly:**

1. **Foreign keys on `qa_defects.scope_task_id` and `scope_feature_id`.** Both columns remain **nullable**, both-null remains valid, and both-set remains rejected (ADR-004 4.8). A referential foreign key makes a **nonexistent** identifier unstorable. **This closes Blueprint §14 item 19** — the question ADR-004 4.16 left unresolved and directed to "be addressed when the persistence / context-loader layer is designed". A dangling reference is no longer representable, so only *unresolved* scope (both null) and *different-Feature* scope (ADR-004 4.14, out of scope and non-blocking) remain. **ADR-004 4.16's ruling about the Checkpoint 3 rule layer is unchanged**: the seven-fact `RuleContext` gains nothing, no `known_feature_ids` fact is added, and the rule layer still makes no existence claim.
2. **`UNIQUE` on `features.slug`.** No domain validator states that slugs are unique; the constraint is recorded here as a deliberate ruling rather than absorbed silently.
3. **Lifecycle statuses stored as `VARCHAR` with a `CHECK` constraint, not as native PostgreSQL `ENUM` types.** This decision names `CHECK` constraints and not enum types, and deferred states — **D-1 `BLOCKED`** foremost — are expected to be added later. Extending a `CHECK` is one migration statement; `ALTER TYPE` is not. **No deferred state is added to any constraint at Checkpoint 4.**

Constraints mirroring existing domain validators — singular defect scope association, evidence attachment, worker evidence never OS-verified, revision numbering, timestamp ordering, checksum format — encode nothing the domain does not already enforce.

**Affects.** Blueprint §7.1, §14 item 19, §15 Checkpoint 4.

### 5.15 Reaffirmed, Not Newly Decided

**Decision.** The following are confirmed for Checkpoint 4 and introduce nothing new:

- **PostgreSQL, SQLAlchemy, and Alembic** — already decided by [ADR-002](ADR-002.md).
- **No caching in Checkpoint 4** — reaffirms ADR-002's *Initial Non-Requirements*, which lists Redis among deliberately deferred infrastructure.
- **SQLAlchemy's standard connection pool** — already configured in `storage/database.py` at Checkpoint 1.

**No new runtime dependency is introduced at Checkpoint 4.**

**Affects.** Nothing. Recorded so the confirmation is traceable.

## Consequences

### Positive

- The Rule Engine acquires a fact source **without acquiring a database dependency**: repositories exist, the context loader that would connect them does not, and Checkpoint 3's isolation is left structurally intact.
- Three conflicts between authoritative records — Actor tables, `work_packages` classification, and event-table ownership — are **resolved rather than absorbed**.
- A lost update becomes a **reported conflict** rather than a silent overwrite (§5.6).
- Audit history cannot be destroyed through the persistence layer: no delete exists to call, and no cascade removes a record the caller never named (§5.7).
- **§14 item 19 is closed by construction** rather than by a rule that would have had to be invented (§5.14).
- Domain determinism is preserved end to end: one identity source, one domain clock, and persistence metadata that never enters a domain object (§5.9).
- A corrupt stored row becomes a **visible failure** rather than a silently repaired object (§5.3).

### Trade-offs

- **The field list is written twice** — once as a Pydantic domain model, once as a SQLAlchemy table — plus a mapper between them. This is the direct cost of the frozen, I/O-free domain layer that lets Checkpoint 3's suite run without a database. A parity test pins the two field sets so they cannot drift unnoticed.
- **Append-only is enforced by construction, not by database trigger.** §5.14 names declarative constraint types only, and a `CHECK` cannot prevent an `UPDATE`. Combined with §5.7 and §5.4 the guarantee is that *no code path capable of updating a historical table exists* — weaker than an independently enforced guarantee in ADR-001's sense, because anything holding a raw session could still bypass it. **Recorded as a known limitation, not claimed as enforcement.**
- **`features.slug` gains a uniqueness rule the domain model does not state** (§5.14).
- **Checkpoint 4 delivers no observable behaviour.** Nothing calls a repository until Checkpoint 6. Its correctness is established entirely by tests.
- **The transaction owner does not exist yet.** §5.5 assigns the boundary to a service/use-case layer that is the Checkpoint 6 Kernel, so Checkpoint 4's integration tests stand in as the caller.
- **Persistence metadata timestamps are a latent hazard.** They are exactly the shape of the mechanism ADR-004 4.15 forbids inventing. §5.9's prohibition on using them for ordering, filtering, or QA-result selection must be enforced by test, not by memory.

## Foundation v1 Scope Boundary

Confirmed **in scope** for Foundation v1 Checkpoint 4, as clarified by this ADR:

- SQLAlchemy ORM models for the fourteen tables listed under *Implementation impact*.
- Explicit domain ↔ row mappers, with domain reconstruction that fails rather than repairs.
- A generic base repository plus domain-specific repositories returning domain objects only.
- A Unit of Work session-scope mechanism, owning no business transaction boundary.
- Optimistic-lock versions on the five mutable-state tables.
- Alembic migrations grouped by coherent schema change, after an untouched `0001_baseline`.
- A persistence exception hierarchy in `storage`.
- Database constraints for fundamental data integrity, and evidence-based indexes.
- Persistence integration tests and architectural boundary tests.

Confirmed **out of scope** for Foundation v1 Checkpoint 4:

- The OS Kernel, the transaction runner, and the **context loader** (Checkpoint 6).
- Any service or use-case class that owns a business transaction (Checkpoint 6).
- `os_events`, `state_transitions_audit`, the event model, and the LISTEN/NOTIFY bus (Checkpoint 5).
- Any FastAPI router, request schema, or transport error mapping (Checkpoint 7).
- The `OSClient` SDK and the vertical slice test (Checkpoint 8).
- Any new rule, transition condition, `RuleContext` fact, or lifecycle state.
- Reviewer routing, QA authoritative-result selection, and the Feature supersession lifecycle.
- **D-1** `BLOCKED` and **D-6** stop / abandon lifecycle.
- Coordinator lifecycle persistence and the Domain Registry (**D-2**, **D-3**).
- Generic CRUD, generic delete semantics, caching, database views, background workers, and any AI provider, model, or agent-runtime coupling.
