# ADR-003: Foundation v1 Domain Model & Lifecycle Clarifications

## Status

Proposed — awaiting Builder approval of this record.

The underlying rulings have been made by the Builder. This ADR records them.

---

## Context

Design Sessions 001–009 established and froze the architecture of **AI Engineering OS**. [ADR-001](ADR-001.md) established independent verification. [ADR-002](ADR-002.md) established the technology foundation. The [Implementation Blueprint](../docs/02-implementation/Implementation-Blueprint.md) translated that frozen architecture into a concrete engineering plan.

Checkpoint 2 of that blueprint implemented the pure domain layer (`domain/`) and the deterministic lifecycle state machines (`state/`).

Turning the architecture into executable domain concepts surfaced a set of points where the authoritative documents were **silent, underspecified, or internally inconsistent**. None of these are architectural disagreements. They are places where an implementer must choose something, and where choosing silently would have amounted to inventing architecture.

This ADR records the Builder's resolution of those points.

**This ADR is a clarification record. It does not replace, restate, or redesign the architecture.**

| :--- | :--- | :--- |
| 1 | `TaskRevision.status: RevisionStatus` declared with no enumerated members | Gap |
| 2 | `TaskRevision.review_decision_id` references an entity that is never modelled | Gap |

| 5 | Work Package lifecycle has states and invariants but no authority table | Gap |

Items 3 and 9 are genuine contradictions **inside the Implementation Blueprint**. Items 6 and 10 touch material the Design Sessions deliberately left open or that Foundation v1 does not yet need. The remainder are omissions.

## Decisions

Each decision below separates three things explicitly:

- **Existing architectural requirement** — already stated in DS-001–009, ADR-001, ADR-002, or the Blueprint. Not decided here.
- **Clarification** — what this ADR resolves.
- **Explicit deferral** — what Foundation v1 will *not* implement, and what remains owed.

### 3.1 Task Revision Status

**Decision.** Remove the stored `RevisionStatus` from `TaskRevision`. The authoritative active-revision pointer is `Task.active_revision_number`. A revision's active-ness is derived from the Task's pointer and the revision history, never stored on the revision itself.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Task Revisions are strictly additive; history is never overwritten, mutated, or discarded (DS-006; DS-009 "OS as the System of Record"; Blueprint §4.1 #4). At any point in time only one Revision is active (DS-006). `Task.active_revision_number` already exists (Blueprint §4.1 #3). |
| **Clarification** | The `status (RevisionStatus)` attribute declared in Blueprint §4.1 #4 is removed. DS-006's "only one Revision is active" is preserved as a **derived invariant**, not a stored flag. |
| **Explicit deferral** | None. |

**Rationale.** A stored `ACTIVE`/`SUPERSEDED` marker requires writing to an already-recorded revision when the next one is appended. Blueprint §7.1 places `task_revisions` under **append-only history**, so at Checkpoint 4 that becomes an `UPDATE` against a table the architecture declares immutable. Since the Task already owns the active pointer, the stored status is both redundant and in conflict with the immutability invariant.

**Affects.** Blueprint §4.1 #4 and §7.1. Requires code change.

### 3.2 ReviewDecision Remains Distinct From Decision

**Decision.** `ReviewDecision` is a distinct domain entity. It is not merged into `Decision`.

- `Decision` — architectural, system-level, and business escalation decisions, with acknowledgements (DS-008).
- `ReviewDecision` — an independent review outcome for one `TaskRevision`: reviewer, outcome (`APPROVED` / `CHANGES_REQUESTED`), and mandatory notes.

| | |
| :--- | :--- |
| **Existing architectural requirement** | `TaskRevision.review_decision_id` exists (Blueprint §4.1 #4). A reviewer outcome with review notes / explicit feedback is mandatory (Blueprint §5.2). Reviewers never modify Worker Revisions; they only produce review decisions (DS-006). |
| **Clarification** | The referenced entity is `ReviewDecision`, distinct from the `Decision` entity of Blueprint §4.1 #8. |
| **Explicit deferral** | None. |

**Rationale.** Merging them would place every routine code review into permanent architectural decision history (DS-009), and would break decision authority, since `REVIEWER` holds authority at no `DecisionScope`.

**Affects.** Blueprint §4.1 (new entity), §4.1 #4, §4.1 #8. No code change — already implemented this way.

### 3.3 BLOCKED Deferred From Foundation v1

**Decision.** Foundation v1 state machines define no `BLOCKED` state. The `BLOCKED` reference in the Blueprint §6 event table is a **future capability**, not a current state. The Blueprint requires a correction so it no longer claims `BLOCKED` is a Foundation v1 state.

| | |
| :--- | :--- |
| **Existing architectural requirement** | An Orchestrator decision may invalidate work in progress. The OS must prevent affected Workers from continuing knowingly invalid work; the current work must be preserved; the Coordinator determines whether it resumes, is reused, is abandoned, or is redirected (DS-008). |
| **Clarification** | Blueprint §5.1 and §5.2 are correct as written. Blueprint §6's `EscalationRaised` row incorrectly records a state change to `BLOCKED`. |
| **Explicit deferral** | **Escalation blocking is not implemented in Foundation v1.** The DS-008 requirement above is knowingly unserved in v1 and remains owed. |

**Rationale.** The Foundation v1 vertical slice (Blueprint §10) contains no escalation path, so v1 has no consumer for the state. Adding states to a frozen state machine without a consuming workflow would be over-design. The DS-008 requirement is not withdrawn — it is deferred.

**Constraint.** The future `BLOCKED` capability **must be designed explicitly** — entry states, exit states, and initiating authority — before any implementation.

**Affects.** Blueprint §5.2 (footnote), §6 (correction), §14. No code change.

### 3.4 Feature Plan Authority & Lifecycle

**Decision.** The Coordinator owns Feature Plan lifecycle transitions. Foundation v1 defines exactly four transitions:

| From | To | Initiator |
| :--- | :--- | :--- |
| `DRAFT` | `READY` | `COORDINATOR` |
| `READY` | `ACTIVE` | `COORDINATOR` |
| `ACTIVE` | `COMPLETED` | `COORDINATOR` / `OS` — `OS` only when completion is deterministically derived from prerequisites |
| `ACTIVE` | `SUPERSEDED` | `COORDINATOR` |

`DRAFT → SUPERSEDED` and `READY → SUPERSEDED` are **not** permitted in Foundation v1.

| | |
| :--- | :--- |
| **Existing architectural requirement** | The Coordinator owns the Feature Plan (DS-009). Plan lifecycle `DRAFT → READY → ACTIVE → COMPLETED` (DS-009). A plan is revised into a new revision rather than silently overwritten; complete planning history is preserved (DS-009). |
| **Clarification** | Requester authority per transition; `OS` co-authority on derivable completion; `SUPERSEDED` is entered only from `ACTIVE`. |
| **Explicit deferral** | Supersession of a `DRAFT` or `READY` plan is excluded from Foundation v1. |

**Rationale.** DS-009's scope-change example depicts revision during active work, which is the scenario `ACTIVE → SUPERSEDED` serves. `OS` co-authority on completion mirrors Blueprint §5.1's `IN_PROGRESS → IN_VALIDATION` (`COORDINATOR` / `OS`). Widening authority later is additive.

**Affects.** Blueprint §5 (new §5.4 — the plan lifecycle is currently absent from §5). No code change — already implemented this way.

### 3.5 Work Package Single-Authority Projection Model

**Decision.** The Work Package lifecycle uses a single authority model.

- `DRAFT → SUBMITTED` — initiator `WORKER`.
- **All subsequent transitions are OS projections** of the corresponding Task lifecycle outcome, with initiator `OS`.

Reviewer, QA, and Coordinator hold **no independent authority over Work Package state**. The actor performs the action at the Task level; the OS maintains the Work Package projection.

| Work Package edge | Initiator | Driven by |
| :--- | :--- | :--- |
| `DRAFT` → `SUBMITTED` | `WORKER` | Task `IN_PROGRESS → SUBMITTED` |
| `SUBMITTED` → `VALIDATED` | `OS` | OS Stage 1 mandatory-evidence validation (DS-005) |
| `VALIDATED` → `REVIEWED` | `OS` | Task `IN_REVIEW → IN_QA` / `→ REVISION_REQUIRED` |
| `REVIEWED` → `ACCEPTED` | `OS` | Task `IN_QA → ACCEPTED` |
| `REVIEWED` → `REJECTED` | `OS` | Task `→ REVISION_REQUIRED` |

| | |
| :--- | :--- |
| **Existing architectural requirement** | The Worker submits the Work Package (Blueprint §5.2, §6; DS-003). A submitted Work Package is immutable and no actor may edit it; fixes require a new Revision and a new Work Package (Blueprint §5.3; DS-003). Evidence verification is hybrid: OS Stage 1, Reviewer Stage 2 (DS-005). |
| **Clarification** | Blueprint §5.3 gains an authority table. After `SUBMITTED`, Work Package state is an OS projection rather than an independently actor-requested transition. |
| **Explicit deferral** | None. |

**Rationale.** Assigning per-role authority to Work Package transitions would create a second authority model competing with the Task state machine for the same real-world actions. Keeping authority defined in exactly one place is a direct consequence of the OS being the enforcement layer. Starting narrow is safe: widening authority is additive, narrowing it is breaking.

**Affects.** Blueprint §5.3. Requires code change.

### 3.6 QA Severity, Priority, and Defect Status

**Decision.** `QADefect.severity` and `QADefect.priority` remain non-empty free-text labels. No taxonomy is introduced. `QADefect.status` is enumerated as `OPEN` / `RESOLVED`.

| | |
| :--- | :--- |
| **Existing architectural requirement** | QA assigns an initial Severity and Priority; **the exact Severity/Priority classification system is still open** (DS-004). Defects carry `severity`, `priority`, `is_blocker`, `status` (Blueprint §4.1 #7). Feature Acceptance requires zero unresolved in-scope defects (DS-009). |
| **Clarification** | `status` is enumerated as `OPEN` / `RESOLVED`, which is the minimum vocabulary that makes "unresolved" machine-computable. |
| **Explicit deferral** | The severity/priority taxonomy remains open, exactly as DS-004 left it. |

**Rationale.** OS enforcement needs only two machine-readable facts: whether a defect blocks, and whether it is unresolved. Severity and priority feed Coordinator remediation prioritisation (DS-009), which is agent judgement, not deterministic enforcement. Inventing a scale now would close a question the architecture deliberately left open, against ADR-002's "Complexity Must Be Earned".

**Affects.** Blueprint §4.1 #7. No code change — already implemented this way.

### 3.7 Claim Type Descriptive; Evidence Keyed By Capability

**Decision.** `Claim.claim_type` remains a non-empty descriptive label, not an enumeration. QA `TestResult` remains minimal. **Mandatory System Evidence rules are keyed by Task/Worker capability, not by `claim_type`.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | Evidence requirements are defined by the OS; Workers do not decide the minimum required Evidence; **every Worker type follows predefined Evidence Standards** (DS-005). Reviewers apply engineering judgement to whether evidence supports the claims — Stage 2 (DS-005). The exact QA Report schema and serialised format is a future implementation concern (DS-009). |
| **Clarification** | `claim_type` never feeds a deterministic rule; it serves Reviewer Stage 2 judgement. The Checkpoint 3 `SystemEvidenceRule` must therefore be keyed off `Task.capability`. |
| **Explicit deferral** | The full QA Report schema remains deferred, as already stated by DS-009. |

**Affects.** Blueprint §4.1 #5, §4.1 #7, §15 (Checkpoint 3 description). No code change.

---

### 3.8 Plan-Local TaskDefinition Key

**Decision.** `TaskDefinition` carries a plan-local `key`. Dependencies between planned tasks reference these keys.

| | |
| :--- | :--- |
| **Existing architectural requirement** | The Feature Plan defines the task breakdown and dependencies between Tasks (DS-009); `task_definitions` carry dependency graphs (Blueprint §4.1 #2). The Coordinator creates Tasks only when their dependencies are satisfied; Tasks are not created simply because they may be needed later (DS-007). |
| **Clarification** | Dependency edges reference plan-local keys because OS `TaskId` values do not exist at planning time. |
| **Explicit deferral** | None. |

**Rationale.** Pre-allocating real Task identities during planning would conflict with DS-007's dependency-driven task creation.

**Affects.** Blueprint §4.1 #2. No code change — already implemented this way.

---

### 3.9 Actor Capabilities

**Decision.** `Actor` carries `capabilities`. A Worker must declare at least one capability. Task assignment requires capability matching.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Workers are selected based on required capabilities (DS-002). `READY → ASSIGNED` requires that the Worker ID is active and possesses matching capability; the rejection triggers are worker inactive, nonexistent, or wrong capability (Blueprint §5.2). |
| **Clarification** | The capability set lives on `Actor`. Blueprint §4.1 #9's omission of the field is corrected; without it the §5.2 rule is unenforceable. |
| **Explicit deferral** | None. |

**Affects.** Blueprint §4.1 #9. No code change — already implemented this way.

### 3.10 Coordinator Lifecycle & Domain Registry Deferred

**Decision.** Foundation v1 does **not** implement the Coordinator lifecycle or the Domain Registry. Foundation v1 uses `Actor.is_active` only, where `is_active = True` corresponds to DS-009 `ACTIVE`. Foundation v1 may use the seeded Coordinator described in the vertical slice (Blueprint §10.2, step 2).

| | |
| :--- | :--- |
| **Existing architectural requirement** | The OS maintains an authoritative Domain Registry mapping domains to Coordinators. The Coordinator lifecycle is `PROPOSED → APPROVED → ACTIVE → SUSPENDED → RETIRED`. A `RETIRED` Coordinator never receives new Tasks or Features, while its historical records remain permanently accessible. During the initial operational phase, **Builder approval is required** before a proposed Coordinator becomes `ACTIVE` (DS-009). **All of this remains authoritative and is unchanged by this ADR.** |
| **Clarification** | The Blueprint's `Actor.is_active` is a Foundation v1 simplification, not a replacement for the DS-009 lifecycle. |
| **Explicit deferral** | The five-state Coordinator lifecycle, the Domain Registry, and the Builder-approval registration workflow are deferred from Foundation v1. |

**This is an explicit deferral, not a rejection of the architecture.**

**Constraint.** The full Coordinator lifecycle **must be resolved before the Domain Registry is implemented**. No `coordinators` or Domain Registry persistence may be created until it is.

**Rationale.** The v1 vertical slice seeds exactly one Coordinator by hand, so the proposal/approval workflow has no v1 consumer, and a five-state lifecycle with no registry to attach it to would be over-design under ADR-002. The deferral is recorded because `is_active` cannot express the Builder-approval gate — an authority boundary — and an unrecorded deferral of an authority boundary is indistinguishable from a lost requirement.

**Affects.** Blueprint §4.1 #9, §14, §15 (Checkpoint 4 precondition). No code change.

## Consequences

### Positive

- The append-only history invariant is now structurally enforced rather than merely asserted: no recorded Task Revision is ever written to after insertion (3.1).
- Authority is defined in exactly one place per real-world action. The Work Package no longer carries a competing authority model (3.5).
- Two internal Blueprint contradictions (`BLOCKED`, `Actor.capabilities`) are identified and resolved rather than silently absorbed into code.
- Every deferral is named, justified, and given a gating condition, so nothing is lost by omission.
- No taxonomy, state, or entity was invented to close a question the architecture deliberately left open.

### Trade-offs

- **DS-008's requirement that the OS prevent Workers continuing knowingly invalid work is unserved in Foundation v1** (3.3). This is the most significant consequence of this ADR and is accepted deliberately.
- **The Builder-approval gate on Coordinator activation is not enforced in Foundation v1** (3.10). With a single seeded Coordinator this has no practical effect, but it is an authority boundary that exists on paper and not in code until the deferral is closed.
- `Task.active_revision_number` becomes the single source of truth for active-ness. Persistence (Checkpoint 4) must keep it consistent with revision history; the domain layer exposes a consistency check but cannot enforce it across aggregates (3.1).
- Severity and priority are not queryable in any structured way until a taxonomy is chosen (3.6).

### Implementation impact

Only two of the ten decisions change code written during Checkpoint 2:

| Decision | Impact |
| :--- | :--- |
| 3.1 Task Revision Status | `domain/enums.py`, `domain/task.py`, `domain/__init__.py` and the corresponding revision-history tests |
| 3.5 Work Package authority | `state/work_package_sm.py` and the corresponding state machine tests |

Decisions 3.2, 3.4, 3.6, 3.7, 3.8, and 3.9 confirm the existing implementation. Decisions 3.3 and 3.10 are deferrals with documentation-only impact.

The Implementation Blueprint requires updates in §4.1 (#2, #4, #5, #7, #9, and a new entity), §5.2, §5.3, a new §5.4, §6, §7.1, §14, and §15.

## Questions Explicitly Not Decided Here

These were surfaced during Checkpoint 2 but are **not** resolved by this ADR. They are recorded so they are not mistaken for settled:

1. **In-scope defect identification.** DS-009 gates Feature Acceptance on "zero unresolved **in-scope** defects", but `QADefect` carries no in-scope marker. The Checkpoint 3 acceptance rule cannot be written deterministically until this is resolved. **Must be resolved before Checkpoint 3.**
2. **Task instantiation timing.** DS-007 states Tasks are created only when their dependencies are satisfied; Blueprint §5.1 requires Tasks to be instantiated at plan activation, with §5.2 providing `PENDING_DEPENDENCIES` to park them. **Must be resolved before Checkpoint 6.**
3. **Post-supersession routing.** DS-009 does not state what happens to a Feature when its plan is superseded, or how the successor plan revision is instantiated. Relevant to Checkpoint 6.

## Relationship to Design Sessions 001–009, ADR-001, and ADR-002

**This ADR does not supersede any prior architectural record.**

| Record | Status after ADR-003 |
| :--- | :--- |
| Design Sessions 001–009 | **Authoritative and frozen. Unchanged.** |
| ADR-001 | **Authoritative. Unchanged.** |
| ADR-002 | **Authoritative. Unchanged.** |
| Implementation Blueprint | Requires the clarifying updates listed under Consequences |

Specifically:

- **DS-006** is not modified. Its requirement that only one Revision is active at any point in time is preserved as a derived invariant (3.1). Its requirement that history is never rewritten is what motivated removing the stored status.
- **DS-008** is not modified. Its escalation-blocking requirement is deferred, not withdrawn (3.3, D-1).
- **DS-009** is not modified. Its Coordinator lifecycle, Domain Registry, and Builder-approval policy remain the architecture of record and are deferred, not replaced (3.10, D-2, D-3).
- **DS-004**'s open Severity/Priority question remains open (3.6, D-5).
- **DS-005**'s Evidence Standards model — OS-defined, per Worker type — is the basis for keying evidence rules by capability (3.7).
- **ADR-001**'s independent verification principle is reinforced, not altered: the Work Package projection model (3.5) removes the possibility of an actor advancing a Work Package outside the verification stages defined by the Task lifecycle.
- **ADR-002**'s "Complexity Must Be Earned" is the operative principle behind every deferral recorded here.

**Note.** DS-009 records that a formal ADR supersession/amendment of ADR-001's original linear workflow is owed in a subsequent checkpoint. **ADR-003 is not that record and does not perform that amendment.** It remains outstanding.

## Foundation v1 Scope Boundary

Confirmed **in scope** for Foundation v1, as clarified by this ADR:

- Feature, Feature Plan, Task, Task Revision, Work Package, Evidence, QA Report, Decision, Review Decision, and Actor as pure domain concepts.
- Deterministic lifecycle state machines for Feature, Feature Plan, Task, and Work Package, with explicit per-transition authority.
- Append-only Task Revision history with no post-insertion writes.
- Immutable submitted Work Packages.
- Capability-matched Task assignment.
- A single hand-seeded Coordinator, per Blueprint §10.2.

Confirmed **out of scope** for Foundation v1:

- Escalation blocking and the `BLOCKED` state (D-1).
- The Coordinator lifecycle, the Domain Registry, and Builder-approval registration (D-2, D-3).
- Feature Plan supersession from `DRAFT` or `READY` (D-4).
- A severity/priority taxonomy (D-5).
- Any independent Reviewer/QA/Coordinator authority over Work Package state (3.5).

Nothing in this ADR converts a deferred capability into a Foundation v1 requirement.
