# ADR-008: HTTP Control Plane Architecture & Checkpoint 7 Scope

## Status

**Accepted — 2026-09-05.**

Records the architecture of the HTTP control plane and the scope of Checkpoint 7, prepared following the Checkpoint 7 planning review and before any API code exists.

**It supersedes nothing.** [Blueprint §9.1](../docs/02-implementation/Implementation-Blueprint.md) already specifies the actor-context headers and §14 item 4 already *recommends* them; this record **rules** on that recommendation rather than leaving an implementation to adopt it silently. [ADR-005](ADR-005.md) 5.12 deliberately left the HTTP mapping of persistence errors to this checkpoint, and [8.2](#82-a-refusal-is-422-and-only-a-refusal-is) supplies it. No Design Session, ADR-001 to ADR-007 ruling is altered.

**Two of these rulings are the Builder's and four are the author's**, made under the Builder's standing delegation of 2026-09-05: *architecture and scope decisions come to the Builder; technical detail does not*. Which is which is recorded in the decision map, because a delegated decision is still a decision and the trail should say who made it.

---

## Context

Checkpoints 1 through 6 are delivered and green, and the Foundation v1 Rule Coverage Gate passes ([ADR-007](ADR-007.md), [ADR-004](ADR-004.md) 4.12). **The OS enforces.** A transition whose conditions are not met is refused, the entity is left untouched, and the refusal is recorded durably in the transaction that discovered it.

**It enforces nothing anyone outside the process can reach.** Every caller so far has been a test holding a `UnitOfWork` in the same interpreter. Checkpoint 7 is the first time this system is addressable from outside itself, and that changes the questions being asked of it: not *did the OS decide correctly* but *how does a decision travel, and who is allowed to ask for one*.

Three properties of the existing architecture constrain what this layer may be.

**The `api` layer holds no business logic.** [Blueprint §2.2](../docs/02-implementation/Implementation-Blueprint.md) is explicit: routers, request and response schemas, and role extraction; **not** direct business logic and **not** direct database transactions. It calls the Kernel. ADR-004 4.7 already establishes that only the Kernel mutates, records audit, and publishes events — a second component doing any of that would put the Validation-First ordering of Blueprint §7.2 in two places.

**Errors carry no transport meaning below this layer.** ADR-005 5.12 translates infrastructure failures into `NotFoundError`, `ConcurrencyConflictError` and `PersistenceError` at the repository boundary and states plainly that these carry no HTTP status codes. Nothing beneath `api` knows what a 404 is, and that separation is what this record must supply the other half of.

**The OS is provider-independent.** [Blueprint §9.1](../docs/02-implementation/Implementation-Blueprint.md) forbids any AI SDK import in the OS and requires that every interaction happen over standard HTTP and JSON. Whatever the control plane looks like, it must be equally usable by an agent runner, a test harness, and a shell script.

Turning that into an actual HTTP surface surfaced four questions the record leaves open or merely recommends. This ADR records their resolution.

### 8.1 Caller Identity Is Read From Headers And Resolved Against `actors`

**Existing architectural requirement.** [Blueprint §9.1](../docs/02-implementation/Implementation-Blueprint.md) already names the headers — `X-Actor-ID`, `X-Actor-Role`, `X-Domain-ID` — and requires that caller identity and authority arrive that way rather than through any provider-specific mechanism. §14 item 4 recommends resolving them through FastAPI dependency injection.

**Clarification.** The recommendation is **implemented as written, and ruled rather than adopted**. Every route resolves the calling Actor from `X-Actor-ID` and `X-Actor-Role`, through one dependency.

Resolution is not trust. Three things are checked before any Kernel method is called:

1. The header is present and well-formed. A missing or unparseable `X-Actor-ID` is a malformed request.
2. **The Actor exists in `actors`.** An identifier naming nobody is refused.
3. **The declared role matches the recorded role.** A caller cannot claim `COORDINATOR` because they typed it in a header; the role the Kernel receives is the one on the Actor record.

Point 3 is what makes this worth doing at all. Everything the state machines and the authority rules enforce is keyed off role, so a role taken at face value would make Checkpoint 6's entire authority layer decorative.

**What this is not, stated plainly.** **This is identification, not authentication.** Anyone who can reach the API can send any `X-Actor-ID` and be treated as that Actor. There is no secret, no signature, and nothing an impostor must possess. It is adequate while the OS runs somewhere the Builder controls and every caller is an agent the Builder started; it is **not** adequate on an open network, and this record does not claim otherwise.

**Why not build authentication now.** It was considered and refused. Issuing, verifying, expiring and refreshing credentials is a subsystem in its own right, it is the largest thing Checkpoint 7 could contain, and **none of it is about enforcing engineering rules** — which is the only thing this OS exists to do. Foundation v1 proves the enforcement mechanism; it does not ship to strangers.

**Explicit deferral.** No token issuance, no signature verification, no session, no API key, no per-route permission layer beyond what the state machines and authority rules already enforce. `X-Domain-ID` is accepted and **not** acted on: ADR-003 3.10 defers the Domain Registry, so there is nothing authoritative to resolve it against, and inventing one here would create the persistence that deferral forbids.

### 8.2 A Refusal Is 422, And Only A Refusal Is

**Existing architectural requirement.** [Blueprint §7.2](../docs/02-implementation/Implementation-Blueprint.md) states that the OS returns `422 Unprocessable Entity` with the structured rejection reasons. [ADR-005](ADR-005.md) 5.12 states that `NotFoundError`, `ConcurrencyConflictError` and `PersistenceError` carry no HTTP status codes and that the mapping belongs here.

**Clarification.** The complete mapping:

| Situation | Status | Meaning to the caller |
| :--- | :--- | :--- |
| The OS refused the transition | **422** | Fix what the reasons name, then retry |
| The entity does not exist | **404** | Retrying will never succeed |
| The entity changed since it was read | **409** | Read it again and retry unchanged |
| The request itself is malformed | **400** | The body or headers are wrong |
| The OS failed | **500** | Not the caller's fault |

**Every refusal the OS makes is a 422**, whether the state machine refused it (the edge is undefined, the initiator is unauthorised) or the Rule Engine did. They are one concept — *the OS declined* — and they arrive in one body carrying the same structured reasons the audit ledger recorded.

**An unauthorised role is a 422, not a 403.** This is the ruling most likely to be second-guessed, so the reasoning is recorded. In this architecture an unauthorised initiator is not an access-control failure at the perimeter: it is `TransitionRejectionCode.UNAUTHORIZED_INITIATOR`, produced by the same state machine evaluation that produces every other refusal, recorded in the same audit ledger, alongside reasons that may well include rule failures too. Splitting it into a 403 would put one idea in two places and force a caller to parse two response shapes to learn one thing.

**Why not one code for everything.** Collapsing 404 and 409 into 422 was considered and refused. A caller cannot tell "you forgot the verification guide" from "that Task does not exist" if both arrive identically, and the difference decides whether retrying is sensible or futile. The line is drawn where a caller's next action differs.

**The refusal body carries the reasons, not a message.** The structured reasons the runner already builds — source, rule id, condition, stable code, human-readable message — are what the response contains. A caller branches on the code; a person reads the message. Free-form text is never the machine contract (ADR-004 4.5), and that holds across the wire.

**Explicit deferral.** No RFC 9457 `application/problem+json` envelope, no error catalogue endpoint, no localisation, and no retry-after hinting.

### 8.3 Named Action Endpoints, Not A Generic Transition Endpoint

**Existing architectural requirement.** [Blueprint §15 Checkpoint 7](../docs/02-implementation/Implementation-Blueprint.md) names six routers — `features`, `tasks`, `submissions`, `reviews`, `qa`, `decisions` — and requires automatic OpenAPI documentation.

**Clarification.** Each Kernel operation is exposed as its own **named** endpoint describing the action in the caller's terms — `submit`, `assign`, `approve`, `accept`, `activate`, `return-for-rework` — rather than as one generic endpoint per entity taking a target state in its body.

**Why.** Three reasons, in order of weight.

**Each endpoint can demand exactly the right information.** Assignment needs a Worker; routing for review needs nothing; plan activation needs a Plan. A generic endpoint must accept a body that is sometimes one shape and sometimes another, so nothing can be validated at the door and every malformed request travels to the Kernel to fail there. Named endpoints reject a wrong-shaped request immediately, with a message naming the field.

**The API is a contract with callers, not a mirror of internals.** `submit` means something to whoever is calling. `{"to": "SUBMITTED"}` requires them to learn the OS's state vocabulary before they can do anything, and couples every caller to state names that are ours to change.

**The generated documentation becomes the list of things the OS can do.** With a generic endpoint, OpenAPI can only say "send a transition".

**The cost, stated.** More endpoints to write and to keep. They are thin by construction ([8.5](#85-a-route-reads-identity-calls-one-kernel-method-and-translates)), so the cost is real but small, and Checkpoint 6 already did the work each one wraps.

**Explicit deferral.** No hypermedia, no discovery endpoint advertising which actions are currently permitted, and no batch or bulk endpoint. A caller learns what is possible from the documentation and from refusals, not from a computed affordance list.

### 8.4 One Transaction Per Request, Opened By The Route, Owned By The Kernel

**Existing architectural requirement.** [ADR-005](ADR-005.md) 5.5: repositories never open a session and never commit; the service layer owns the transaction boundary. ADR-007's runner commits, because the Validation-First invariant depends on the rejection path committing.

**Clarification.** A request opens exactly one `UnitOfWork`, hands it to one `OSKernel`, and that Kernel's runner owns the commit. The route never commits, never rolls back, and never touches a repository.

**One transaction per request, and one Kernel call per request.** A route that needed two Kernel calls would have two commits and therefore two outcomes for one request — a caller could receive a refusal for work that was half applied. If an operation genuinely needs to span two transitions, it belongs in the Kernel as one operation, the way `activate_plan` already does.

**Explicit deferral.** No request-scoped caching, no connection pinning beyond SQLAlchemy's own pool (ADR-005 5.15), no distributed transaction, and no outbox: the notification is already emitted inside the committing transaction (ADR-006 6.2).

### 8.5 A Route Reads Identity, Calls One Kernel Method, And Translates

**Existing architectural requirement.** [Blueprint §2.2](../docs/02-implementation/Implementation-Blueprint.md) forbids `api` from holding direct business logic or direct database transactions. ADR-004 4.7 makes the Kernel the only component that mutates, audits and publishes.

**Clarification.** Every route does exactly three things, in this order:

1. Resolve the calling Actor ([8.1](#81-caller-identity-is-read-from-headers-and-resolved-against-actors)).
2. Call **one** Kernel method.
3. Translate the `TransitionResult` into a response ([8.2](#82-a-refusal-is-422-and-only-a-refusal-is)).

**No route evaluates a rule, reads a repository, inspects a state machine, decides a status by inspecting entity state, or writes anything.** A route that needs a fourth kind of step is evidence that logic has landed in the wrong layer, and the rule above makes that visible immediately rather than after it has spread.

**This is what makes the thinness an alarm rather than a style preference.** The temptation in an HTTP layer is always to check one small thing before calling down — whether the Task exists, whether the caller is plausibly allowed. Every such check is enforcement outside the enforcement layer, and it is how a second, quieter, untested copy of the rules comes into existence.

**Explicit deferral.** No middleware performing authorisation, no request validation beyond schema shape, and no response filtering by role. What a caller may see is not modelled in Foundation v1.

### 8.6 Checkpoint 7 Exposes No Event Stream

**Existing architectural requirement.** Checkpoint 6 appends an `OSEvent` for every evaluated transition and emits its notification inside the committing transaction (ADR-006 6.2, 6.9). [ADR-006](ADR-006.md) 6.5 deferred per-event-type payload schemas for want of a consumer; [the UI](../ui/README.md) is that consumer and is parked.

**Clarification — the Builder's ruling.** **Checkpoint 7 builds the control plane only: endpoints for *doing* things, none for *watching* them.** No event-stream endpoint, no polling endpoint, no server-sent events, no WebSocket. Reading the event stream becomes its own piece of work, taken up **immediately after** Checkpoint 7 and with its own decision record.

**Why not now, when the events exist and the UI is waiting.** Checkpoint 7 is already the first time this system is reachable from outside, which is enough new ground for one checkpoint. And *how a live view reads a growing event stream without hammering the database* is a real design question — polling interval, resume position, back-pressure, what a reconnecting client is owed — that deserves its own thinking rather than a corner of a checkpoint about endpoints.

**What this costs, stated honestly.** The UI stays on scripted events for one checkpoint longer. That was the Builder's own trade to make and the Builder made it.

**Consequence for ADR-006 6.5.** The payload schemas stay deferred, and the reason is now sharper rather than vaguer: the consumer exists, but the mechanism it will consume through does not, and shaping an append-only payload for a transport nobody has designed is exactly the guess ADR-006 6.5 declined to make.

**Explicit deferral.** The whole of it: event read endpoints, subscription, filtering, replay, and any UI wiring. Recorded as **next**, not as someday.

### 8.7 Reaffirmed, Not Newly Decided

- **The Kernel remains the only component that mutates, audits and publishes** (ADR-004 4.7). `api` adds no fourth writer.
- **ADR-005 5.12 stands.** Persistence errors still carry no status code; 8.2 maps them at this boundary and changes nothing beneath it.
- **Blueprint §9.1 provider independence stands.** No AI SDK is imported, and every interaction is HTTP and JSON.
- **ADR-003 3.10 stands.** `X-Domain-ID` is accepted and unused; no Domain Registry is created.
- **The typed client SDK is Checkpoint 8** (Blueprint §9.2), not this one.
- **No new runtime dependency.** FastAPI, Pydantic and uvicorn were installed at Checkpoint 1 (ADR-002).

## Consequences

### Positive

- **The OS becomes reachable**, and Checkpoint 6's enforcement becomes something an agent, a script or a person can actually be refused by.
- **The refusal survives the wire intact.** The stable codes the Rule Engine emits reach the caller unflattened, so another program can branch on them rather than parse prose.
- **Checkpoint 7 stays small.** One concern — doing things over HTTP — with the watching half deliberately held back.
- **The thin-route rule gives an early alarm** for logic drifting into the wrong layer, at the moment it happens rather than a checkpoint later.

### Trade-offs

- **Identification is not authentication** (8.1). Anyone who can reach the API can impersonate any Actor. This is the largest recorded limitation in the system and it is accepted deliberately for Foundation v1.
- **More endpoints than a generic design would need** (8.3), each thin but each one more thing to keep consistent.
- **A 422 covers a wide range** (8.2). "Unauthorised role" and "missing evidence" arrive with the same status, and a caller that only reads the status learns less than one that reads the reasons. The reasons are the contract; the status is a category.
- **The UI waits another checkpoint** (8.6).
- **Nothing here is enforced by construction.** The thin-route rule (8.5) and the one-Kernel-call rule (8.4) are conventions this record states; a route violating either still runs. They need tests, in the same way ADR-006 6.9 and ADR-007 7.4 did.

### Implementation impact

Checkpoint 7 work created by this record:

| Area | Change |
| :--- | :--- |
| `api/dependencies.py` | Actor resolution from headers; the `UnitOfWork` and `OSKernel` per-request dependencies |
| `api/errors.py` | The 8.2 mapping, as exception handlers; the refusal response schema |
| `api/schemas/` | Request and response models per action — Pydantic, no domain models on the wire |
| `api/routers/` | `features`, `tasks`, `submissions`, `reviews`, `qa`, `decisions` |
| `main.py` | Router registration; OpenAPI metadata |

Required checks, in addition to the existing suite:

- A refusal returns 422 carrying the same structured reasons the audit ledger recorded.
- A refused request leaves the entity unchanged **and** its audit record present — the Blueprint §7.2 invariant, now asserted through HTTP.
- A header role that disagrees with the recorded Actor role is refused.
- An unknown `X-Actor-ID` is refused.
- `NotFoundError` maps to 404 and `ConcurrencyConflictError` to 409.
- **No route module imports `storage`, `rules`, `state` or `events`** — the structural expression of 8.5, and the check that keeps the thin-route rule from decaying into a comment.

## Questions Not Decided In This Record

1. **How the event stream is read.** Deferred by [8.6](#86-checkpoint-7-exposes-no-event-stream) and taken up next. Polling versus streaming, resume position, and what a reconnecting client is owed are all open.
2. **Per-event-type payload schemas** ([ADR-006](ADR-006.md) 6.5). Still deferred, now for a sharper reason.
3. **Authentication.** Deferred by [8.1](#81-caller-identity-is-read-from-headers-and-resolved-against-actors). Recorded as a known limitation of Foundation v1, not as a backlog item to be picked up quietly.
4. **Authorisation beyond role.** What a caller may *see*, as opposed to what they may *do*, is not modelled anywhere.
5. **`X-Domain-ID`'s meaning**, which waits on the Coordinator lifecycle and Domain Registry (ADR-003 3.10).
6. **Reviewer workload and fairness** ([ADR-007](ADR-007.md) 7.3), and **non-blocking work** ([ADR-007](ADR-007.md) 7.1). Unchanged by this record.

## Foundation v1 Scope Boundary

**In scope, created by this record:** the `api` package — header-based Actor resolution, the HTTP status mapping and refusal schema, request and response models, six routers of named action endpoints, and one transaction per request.

**Out of scope, explicitly:** authentication of any kind; authorisation beyond role; any event read, subscription or streaming endpoint; UI wiring; hypermedia or affordance discovery; batch endpoints; pagination beyond what a listed collection needs; rate limiting; CORS policy; the typed client SDK (Checkpoint 8); and any Domain Registry behaviour behind `X-Domain-ID`.

**What comes immediately after:** the event read mechanism, with its own record. It is the last thing standing between [the UI](../ui/README.md) and real data.
