# ADR-002: Implementation Foundation & Technology Stack

## Status

Accepted for initial implementation.

## Context

Design Sessions 001 through 009 established the core architecture of **AI Engineering OS** as the deterministic operating layer surrounding the multi-agent engineering workflow.

The OS is responsible for state management, transition enforcement, event routing, rule validation, permission checks, evidence tracking, decision history, and immutable revision management without acting as an AI manager or active polling supervisor.

To begin implementation, the OS requires a reliable, durable, and extensible foundation for:

- State persistence and lifecycle transitions
- Workflow rules and permission enforcement
- Event persistence and dispatching
- System and Worker Evidence records
- Architectural decisions and acknowledgement records
- Immutable Task Revisions and Work Packages
- Machine-first QA Reports and findings
- Auditability and complete historical records
- Agent coordination and tool integrations
- Repository inspection and command execution

A technology foundation must be selected that satisfies these core invariants while keeping complexity strictly earned.

---

## Decision

The initial AI Engineering OS implementation will use the following technology stack:

- **Language:** Python 3.13+
- **API / Control Plane:** FastAPI
- **Structured Models & Validation:** Pydantic
- **Database / System of Record:** PostgreSQL
- **ORM / Data Access:** SQLAlchemy
- **Database Migrations:** Alembic
- **Event Persistence:** PostgreSQL
- **Initial Event Wake-up:** PostgreSQL LISTEN/NOTIFY
- **Containers / Local Infrastructure:** Docker + Docker Compose
- **Testing:** pytest
- **Linting & Formatting:** Ruff
- **Static Type Checking:** mypy

---

## Why This Stack

- **Python 3.13+:** Selected because the OS heavily interacts with AI/agent tooling, code analysis, repository automation, structured data, and orchestration libraries. Python provides mature ecosystem support for agentic systems and CLI tooling.
- **FastAPI:** Provides a lightweight, high-performance API and control-plane layer with native async support and OpenAPI documentation.
- **Pydantic:** Provides strict structured validation, serialization, and schema generation for OS domain objects, requests, Work Packages, QA Reports, and events.
- **PostgreSQL:** Serves as the authoritative, transactional system of record for durable state, events, revisions, and audit history.
- **SQLAlchemy:** Provides a clean, type-safe data-access and ORM layer for interacting with PostgreSQL.
- **Alembic:** Provides deterministic, version-controlled database schema migrations.
- **Docker Compose:** Provides a lightweight, reproducible local development and execution environment.
- **pytest, Ruff, mypy:** Provide baseline engineering quality controls, fast linting/formatting, and strict static type verification.

---

## Event Architecture

The OS is fundamentally event-driven.

- **PostgreSQL is the durable source of truth.**
- **LISTEN/NOTIFY is only an initial wake-up/notification mechanism.** It is **not** the authoritative event store.
- **Core Principle:** Persist the relevant state and event information durably before relying on a notification to wake another process.

If a process crashes or misses a transient notification, the system must always be able to recover cleanly by reading persisted state and unhandled events directly from PostgreSQL.

### Event Flow Model

```
Event occurs
    ↓
Persist state / event in PostgreSQL
    ↓
Database transaction commits
    ↓
PostgreSQL LISTEN/NOTIFY notification emitted
    ↓
Interested component wakes
    ↓
Reads authoritative state from PostgreSQL
```

---

## Workflow Engine

The initial implementation will contain an **explicit, OS-owned state, transition, and rule layer**.

- Do **not** make Temporal, Kafka, Redis, RabbitMQ, or any other external workflow or event system a mandatory foundation dependency at this stage.
- The domain model, lifecycle state machines, and transition rules must remain directly owned and enforced by AI Engineering OS.
- External durable-execution engines (such as Temporal) may be evaluated in future iterations if demonstrated durable-execution requirements justify them.

---

## Complexity Must Be Earned

The initial implementation should use the smallest infrastructure that can reliably satisfy the defined AI Engineering OS invariants.

Additional infrastructure, services, frameworks, or external systems should be introduced only when a demonstrated requirement justifies their operational and architectural complexity.

The absence of Redis, Kafka, RabbitMQ, Temporal, Kubernetes, or other advanced infrastructure from the initial foundation is intentional, not a limitation.

Future infrastructure may be introduced when actual requirements justify it and should preferably sit behind appropriate abstractions.

**Do not introduce technology merely because it is popular, scalable in theory, or available.**

---

## Initial Non-Requirements (Deferred Infrastructure)

The following technologies are deliberately **not required** for Foundation v1:

- Redis
- Kafka
- RabbitMQ
- Temporal
- Kubernetes
- Distributed microservices
- Complex message brokers
- Large-scale distributed infrastructure

This does not permanently reject these technologies. They can be evaluated when real operational requirements emerge.

## Database Principles

PostgreSQL is the authoritative system of record.

The OS will eventually persist:
- Features and Feature Plans
- Tasks and Task Revisions
- Work Packages (Summary, Claims, Evidence, Worker Notes)
- System Evidence and Worker Evidence
- QA Reports, Test Results, and Defects
- Architectural Decisions, Rationale, and Acknowledgements
- Domain and Coordinator Registries
- Events, State Transitions, and Validation Audit Logs
- Permissions and Actor Roles

### Database Rules
1. **Schema Deferred to Blueprint:** The complete database schema is not defined in this ADR and will be designed during the implementation blueprint.
2. **Controlled Migrations:** All schema changes must be versioned and executed exclusively through Alembic migrations.
3. **Restricted Access:** Agents and Workers must never independently alter the OS database schema.

---

## Container Principles

- Docker Compose is the initial local infrastructure strategy.
- Keep the initial container environment intentionally minimal (e.g., application service + PostgreSQL).
- Do not create unnecessary sidecars, caches, or background worker containers before the architecture requires them.

---

## Testing Principles

Automated testing must verify both:
1. **Standard Software Behavior:** Correct CRUD operations, endpoint responses, schema parsing, and database transactions.
2. **AI Engineering OS Invariants:**
   - Invalid workflow transitions are deterministically rejected.
   - Transitions missing mandatory System Evidence (diffs, test runs, build logs) are rejected.
   - Feature Acceptance strictly requires a valid QA Final Pass with zero unresolved blockers.
   - Actor permissions and role boundaries are strictly enforced.
   - Historical records and Revisions are immutable and never silently overwritten.
   - Invalid workflow states cannot be created through normal OS interfaces.

---

## Provider Independence

The AI Engineering OS runtime architecture must remain independent from any specific AI provider or model.

- Current development resources available to the Builder are documented separately in [brain/Development-Resources.md](../brain/Development-Resources.md). That document tracks tools available while building the OS and is **not** part of this architectural decision.
- The OS runtime must not be coupled to Claude, Gemini, Codex, any single foundation model, or any proprietary AI coding environment.
- Agent execution and model integrations will be designed behind modular provider abstractions during the implementation blueprint.

---

## Non-Goals of this ADR

This ADR deliberately does **not** define:
- Complete database schemas and table structures
- Complete API endpoint lists and route handlers
- Exact JSON/YAML event payload schemas
- Agent prompt templates and system prompts
- LLM model selection and token budget allocation
- Full agent runtime and sandboxing implementations
- Production cloud infrastructure and deployment topology
- Kubernetes manifests and cluster orchestration
- High-throughput distributed scaling strategies
- Complete frontend UI architecture

These concerns belong to subsequent design checkpoints and implementation blueprints.

---

## Rationale & Consequences

### Rationale
The selected foundation is intentionally **boring, understandable, durable, and extensible**. 

The goal is not to maximize the number of technologies or introduce theoretical distributed systems prematurely. The goal is to build a rock-solid, transactional core that reliably enforces the OS's fundamental invariants while allowing complexity to be introduced only when real requirements justify it.

### Consequences
- **Positive:**
  - High developer ergonomics and rapid initial development velocity.
  - Zero external broker/engine dependencies for local development.
  - Strong ACID guarantees for all state transitions, events, and audit records in PostgreSQL.
  - Strict type-safety and data validation via Python 3.13+, Pydantic, and SQLAlchemy.
  - Full architectural independence preserved for future scaling or workflow engine adoption.
- **Trade-offs:**
  - Initial event wake-up via PostgreSQL LISTEN/NOTIFY requires polling-based fallback or reconnection logic for disconnected consumers.
  - Long-running worker processes must be managed via standard application lifecycles rather than an external orchestrator like Temporal until requirements demand it.
