# ADR-006: Event Layer Architecture & Checkpoint 5 Scope

## Status

**Accepted — 2026-09-04. Amended 2026-09-04** — see [Amendment](#amendment--checkpoint-5-implementation-ruling-2026-09-04).

§6.11 was added on 2026-09-04 by Builder ruling, following a circular dependency discovered while implementing this checkpoint. **§6.1–§6.10 stand unchanged.**

Records the event and notification architecture for Foundation v1 and the scope of Checkpoint 5, prepared following the Checkpoint 5 planning review.

This ADR is an implementation-foundation and clarification record for the event layer. **It does not replace, restate, or redesign the architecture.** It supersedes exactly one prior record: the Implementation Blueprint §7.2 step 7 *illustration* of post-commit notification (see [6.2](#62-the-notification-is-emitted-inside-the-committing-transaction)). It amends the Blueprint §7.2 description of what `state_transitions_audit` records ([6.3](#63-the-transition-audit-records-both-outcomes)) and the channel name that section names ([6.7](#67-a-single-notification-channel)). No Design Session, ADR-001, ADR-002, ADR-003, ADR-004, or ADR-005 ruling is altered.

---

## Context

Design Sessions 001–009 froze the architecture. [ADR-002](ADR-002.md) named PostgreSQL the authoritative system of record and named PostgreSQL `LISTEN/NOTIFY` the wake-up mechanism, explicitly **not** the event store. [ADR-005](ADR-005.md) 5.13 assigned `os_events` and `state_transitions_audit` — together with their models, migrations, and repositories — to Checkpoint 5, resolving a conflict in which Blueprint §11 marked the event model `[PLANNED — CP4]` while §15 Checkpoint 5 claimed the same artefact, and in which `state_transitions_audit` was owned by no checkpoint at all.

Checkpoint 2 implemented the pure domain layer (`domain/`) and the lifecycle state machines (`state/`). Checkpoint 3 implemented the Rule Engine (`rules/`). Checkpoint 4 implemented the schema, the mappers, the repositories, and the Unit of Work session scope (`storage/`).

**The OS can now remember. It cannot yet announce.** Nothing records that a transition was attempted, nothing records that one was refused, and no component can be woken when something happens. Blueprint §7.2 states the invariant that depends on the first two — *rejected transition = no target-state mutation + durable rejection record* — but the table that rejection record lands in does not exist.

**Checkpoint 5 builds the durable record and the wake-up signal.** It evaluates no rule, validates no transition, and advances no state. The component that will write events during real transitions is the Checkpoint 6 Kernel, which does not exist yet; Checkpoint 5's integration tests stand in as its caller, exactly as Checkpoint 4's did for the repositories.

Turning the event model of Blueprint §6 into relational tables and a notification path surfaced a set of points where the authoritative documents were silent, underspecified, or — in one case — described a sequence that cannot deliver the guarantee ADR-002 claims for it. This ADR records the Builder's resolution of them.

### 6.1 Total Ordering By Database-Generated Sequence

**Decision.** `os_events` and `state_transitions_audit` each carry a **`sequence_number BIGINT GENERATED ALWAYS AS IDENTITY`** column. It is the **sole authority on append order**.

**No timestamp orders events.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | Events are appended in sequential order and that order is verified by test (Blueprint §13). Persistence metadata timestamps **must not be used for ordering or filtering** (ADR-005 5.9, ADR-004 4.15, §14 item 18). Domain timestamps are domain-owned and persisted exactly as produced (ADR-005 5.9). |
| **Clarification** | Blueprint §6 lists `occurred_at` but no ordering key, and a UUID primary key does not sort. The identity column supplies the total order §13 requires without reaching for a timestamp that either record forbids or the domain owns. `GENERATED ALWAYS` — not `BY DEFAULT` — so the application **cannot** supply the value, and the ordering authority cannot be overridden from code. |
| **Explicit deferral** | No cross-table global ordering is defined. Each table is ordered within itself. Nothing orders an `os_events` row relative to a `state_transitions_audit` row, and no consumer may assume one. |

**Rationale.** `occurred_at` is generated by the domain, so two events can share a value and a clock adjustment can invert two others. `row_created_at` is exactly the mechanism ADR-005 5.9 prohibits. A database-assigned identity is monotonic per table, requires no coordination, and — see [6.6](#66-subscribers-resume-by-sequence-position-held-in-memory) — doubles as the subscriber's resume token, which no timestamp can safely be.

Gaps in the sequence are expected and carry no meaning: a rolled-back transaction consumes a value. Consumers compare, never count.

**Affects.** Blueprint §6, §13.

### 6.2 The Notification Is Emitted Inside The Committing Transaction

**Decision.** The notification is emitted with **`pg_notify()` inside the transaction that appends the event**, not after it commits.

**This supersedes the Blueprint §7.2 step 7 illustration.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | All state changes are committed to PostgreSQL **before any notification is published** (Blueprint §3). PostgreSQL is the durable event store; `LISTEN/NOTIFY` is **only a wake-up mechanism** (ADR-002). |
| **Clarification** | PostgreSQL delivers notifications queued by `pg_notify()` **at commit, and only on commit**. Emitting inside the transaction therefore satisfies the §3 ordering requirement exactly — a notification is never delivered for work that did not commit — while removing the window in which committed work is never announced. |
| **Explicit deferral** | No outbox table, no retry queue, and no delivery acknowledgement. None is needed once emission and commit are atomic. |

**Rationale.** Blueprint §7.2 step 7 emits after `commit()` returns. Between those two moments the process can die: the event is durable and no wake-up will ever be sent for it. [6.6](#66-subscribers-resume-by-sequence-position-held-in-memory) makes that survivable rather than fatal — no event is lost — but a connected subscriber that never reconnects has no reason to re-read, and can idle indefinitely on a bell that already failed to ring. Emitting inside the transaction removes the window rather than compensating for it.

**Trade-off, accepted.** A failure in `pg_notify()` now rolls back the transition it accompanied. A transition that commits unobserved is judged worse than a transition that fails visibly and is retried.

**Affects.** Blueprint §7.2 step 7 and its conceptual snippet. **The Validation-First sequence itself — evaluate before mutating, record the rejection durably, commit — is unchanged and remains authoritative.**

### 6.3 The Transition Audit Records Both Outcomes

**Decision.** `state_transitions_audit` records **every evaluated transition attempt**, carrying an **`outcome` column** admitting `ALLOWED` and `REJECTED`.

**It is not a rejection-only table.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | *Rejected transition = no target-state mutation + durable rejection record* (Blueprint §7.2). History is additive; records are never overwritten (Blueprint §3). `StateTransitionAllowed` and `StateTransitionRejected` are both defined event types (Blueprint §6). |
| **Clarification** | Blueprint §7.2 inserts into `state_transitions_audit` on the failure path only, leaving successful transitions recorded solely as an `os_events` row with an unconstrained payload ([6.5](#65-strict-envelope-unconstrained-payload)). The audit table records both, so `from_state`, `attempted_state`, initiator, and outcome are structured columns for every attempt rather than for refusals alone. |
| **Explicit deferral** | The audit table remains a record of **evaluated** transitions. A request rejected before evaluation — an unparseable command, an unknown entity — is not an evaluated transition and produces no audit row. Transport-level rejection recording belongs to Checkpoint 7. |

**Rationale.** An audit table that holds only refusals cannot answer *"what happened to this Task?"*. Answering it would mean parsing free-form `os_events` payloads, which [6.5](#65-strict-envelope-unconstrained-payload) explicitly declines to constrain — placing the enforcement record's structure behind exactly the schema this ADR chose not to fix. Recording both outcomes keeps the enforcement history in typed columns and leaves `os_events` as the general stream.

**Trade-off, accepted.** A successful transition writes two rows — one audit row and one `os_events` row. The duplication is deliberate: the two tables answer different questions, and neither is derivable from the other without the payload schema this ADR defers.

**Affects.** Blueprint §7.2.

### 6.4 A Closed Thirteen-Entry Event Vocabulary

**Decision.** `EventType` is a closed `StrEnum` with **exactly the thirteen entries listed in Blueprint §6**, enforced by a database `CHECK` constraint generated from the enumeration.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Blueprint §6 names thirteen event types. Statuses and enumerated labels are persisted as `VARCHAR` with a `CHECK` generated from the domain enumeration, never a native PostgreSQL `ENUM` (ADR-005 5.14, implemented by `storage/models/base.py::status_check`). No deferred state is admitted by any constraint (ADR-005 5.14). |
| **Clarification** | The event type column uses the same `status_column` / `status_check` mechanism as every other vocabulary in the schema. A misspelled event type is rejected by the database at write time rather than silently creating an event kind no subscriber listens for. |
| **Explicit deferral** | No fourteenth event type is admitted. Adding one is a migration, deliberately. |

**Rationale.** Every other enumerated vocabulary in this system is database-enforced; an open event type column would be the sole exception, and the failure it permits is silent. Generating the constraint from the enumeration rather than hand-listing values is the existing convention and prevents the constraint drifting from the vocabulary.

**`EscalationRaised` is included.** It is one of the thirteen. Blueprint §6 already records it as a forward reference to the deferred escalation-blocking capability. **Recording the event creates no `BLOCKED` state and does not withdraw D-1**, which remains deferred and unimplemented; no status constraint anywhere admits it.

**Affects.** Blueprint §6, §11.

### 6.5 Strict Envelope, Unconstrained Payload

**Decision.** The event **envelope** is strictly typed and validated. The **payload** is a JSON-serialisable mapping with **no per-event-type schema at Checkpoint 5**.

Envelope: `id`, `sequence_number`, `event_type`, `aggregate_type`, `aggregate_id`, `actor_id`, `actor_role`, `occurred_at`.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Blueprint §6 specifies the envelope fields and types the payload as JSONB. History is additive and rows are never rewritten (Blueprint §3, ADR-005 5.8). Complexity must be earned (ADR-002). |
| **Clarification** | Per-event-type payload schemas are **not** authored at Checkpoint 5. The producers and consumers that would constrain them — the Checkpoint 6 Kernel and the Checkpoint 7 API — do not exist. |
| **Explicit deferral** | Payload schemas per event type are **owed to Checkpoint 6 or later**, and are recorded here as an outstanding design task rather than an open architectural question. |

**Rationale.** `os_events` is append-only: a row is never reshaped. A payload schema guessed now, against unwritten consumers, is not corrected later but carried alongside its replacement indefinitely. [6.3](#63-the-transition-audit-records-both-outcomes) materially reduces the cost of waiting — the structured detail the OS actually enforces against now lives in `state_transitions_audit` columns, not in a payload.

**Trade-off, accepted.** An unconstrained payload has no schema discipline and can drift between producers until a later checkpoint tightens it. The audit table, not the payload, is the authoritative enforcement record in the interim.

**Affects.** Blueprint §6.

### 6.6 Subscribers Resume By Sequence; Position Held In Memory

**Decision.** A subscriber tracks the highest `sequence_number` it has processed. On connect and on **every reconnect** it first **reads forward from that position and drains the backlog**, and only then resumes waiting on notifications.

The position is held **in memory**. On a full process restart the subscriber begins from the current end of `os_events`.

| | |
| :--- | :--- |
| **Existing architectural requirement** | PostgreSQL is the durable event store; `LISTEN/NOTIFY` is only a wake-up mechanism (ADR-002). Integration tests must cover "reconnection / state recovery from unhandled events" (Blueprint §13). |
| **Clarification** | ADR-002's claim that the notification is *only* a wake-up is true **only if a missed notification is recoverable**. This decision states the mechanism that makes it true, and fixes the ordering: **drain first, then listen.** Listening before draining permits a newer event to be processed before an older one still in the backlog. |
| **Explicit deferral** | **No durable subscriber position.** Events appended while a subscriber process is entirely down are not replayed to it on restart. No subscriber-position table, no consumer groups, no competing-consumer coordination, and no at-least-once delivery guarantee across restarts. |

**Rationale.** The in-memory position covers the failure this system actually has in Foundation v1 — a dropped or re-established connection — with no new table and no coordination semantics to design. Durable positions raise questions Foundation v1 has no answer for: whether two subscribers share a position or hold their own, and what happens when one falls permanently behind.

**Recorded limitation, not claimed as a guarantee.** *No event is lost* — `os_events` is durable and append-only. *Every event is observed by every subscriber* is **not** guaranteed across a subscriber restart. This is the same class of statement as ADR-005 5.8's append-only-by-construction limitation: recorded honestly rather than overclaimed, and enforced by test that the drain-then-listen ordering holds.

**Affects.** Blueprint §11, §13.

### 6.7 A Single Notification Channel

**Decision.** One notification channel carries every event. Subscribers filter for what concerns them.

**The Blueprint §7.2 channel name `task_events` is replaced.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | `NOTIFY` payloads are capped at 8,000 bytes and must carry a lightweight envelope — never a domain object — with receivers fetching authoritative state from PostgreSQL (Blueprint §14 item 3). Complexity must be earned (ADR-002). |
| **Clarification** | §7.2's `channel="task_events"` implies a per-aggregate channel topology that no record establishes. Foundation v1 uses one channel. The notification payload remains the thin envelope §14 item 3 already specifies: event id, aggregate type, and aggregate id. |
| **Explicit deferral** | No per-aggregate, per-role, or per-tenant channel topology. No channel routing or subscription filtering in the database. |

**Rationale.** Every additional channel requires its own connection, its own reconnect handling, and its own drain-then-listen implementation from [6.6](#66-subscribers-resume-by-sequence-position-held-in-memory) — multiplying the one piece of ordering-sensitive logic in the layer, and with it the chance of getting exactly one instance of it wrong. Foundation v1 has few subscribers, and filtering in the subscriber is a comparison against the envelope. A wake-up carrying no domain data is cheap enough that an unwanted one costs nothing worth optimising.

**Affects.** Blueprint §7.2, §11.

### 6.8 Initiator Attribution And The Null Actor ID

**Decision.** The event's actor role column records an **`Initiator`** — `ActorRole | SystemActor` — admitting seven values: the six Actor roles plus `OS`.

The actor id column is **nullable**, and a `CHECK` constraint permits null **only** when the role is `OS`.

The same applies to `state_transitions_audit`'s `requested_by` / `requested_by_role`.

| | |
| :--- | :--- |
| **Existing architectural requirement** | `SystemActor.OS` exists precisely because "several blueprint transitions declare `OS` as the requester (for example `CREATED -> READY`). The OS is infrastructure rather than an agent, so it is deliberately kept out of `ActorRole`" (`domain/enums.py`, implementing Blueprint §4.1 #9). `TASK_STATE_MACHINE` names `SystemActor.OS` the **sole** permitted initiator of four transitions — `CREATED -> PENDING_DEPENDENCIES`, `CREATED -> READY`, `PENDING_DEPENDENCIES -> READY`, and `SUBMITTED -> IN_REVIEW`. **No Actor role may request any of them.** `Initiator = ActorRole | SystemActor` is the established type for a transition requester. |
| **Clarification** | Blueprint §6 lists `actor_id` and `actor_role` without stating what an OS-initiated event records. The event layer reuses `Initiator` rather than inventing a parallel scheme, and the `actors` table gains **no** row for the OS. The `CHECK` confines the null to the one case that warrants it. |
| **Explicit deferral** | No sentinel actor id, no OS row in `actors`, and **no new vocabulary entry**. `ActorRole` is unchanged. |

**Rationale.** Recording a human requester for `CREATED -> READY` would be false — the OS moves the Task when dependencies clear, and the state machine admits no other initiator. A sentinel UUID would look like an actor id while resolving to no row, so any join to `actors` would silently find nothing. A real `actors` row would place a non-agent into the table the authority rules read from. A guarded null states the truth and confines it.

**Affects.** Blueprint §6, §7.1.

### 6.9 The Bus Receives A Session; The Kernel Owns The Call

**Decision.** `events/bus.py` exposes an emit operation that **takes the caller's session**. The **Checkpoint 6 Kernel** stages the event and emits the notification on that one session.

**Appending an event does not itself emit a notification.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | `events` depends on `domain` and `storage`; `core` depends on `domain`, `state`, `rules`, `events`, and `storage` (Blueprint §2.2). The service/use-case layer owns the transaction boundary; repositories use the session supplied to them and never commit (ADR-005 5.5). Only the Kernel mutates state, records audit, and publishes events (ADR-004 4.7). |
| **Clarification** | [6.2](#62-the-notification-is-emitted-inside-the-committing-transaction) requires the emit to run on the transaction's own session, so the bus cannot be the standalone `notification_bus` object §7.2 depicts. Placing the emit inside the event repository would make `storage` depend on `events`, which already depends on `storage` — the circular dependency §2.2 exists to prevent. The Kernel sits above both and may call each. |
| **Explicit deferral** | **Checkpoint 5 does not wire event recording into any transition.** No Kernel and no transaction runner exist until Checkpoint 6. |

**Rationale.** The layering is the constraint, and it points at exactly one placement. ADR-004 4.7 independently assigns event publication to the Kernel, so this is where the architecture already put it.

**Trade-off, accepted.** Staging an event and emitting the notification are two calls, so a future caller could do the first and omit the second. This is **not** enforced by construction, and the component that would omit it does not exist yet. Recorded as a known limitation and as a **required check at Checkpoint 6**, where the Kernel becomes testable.

**Affects.** Blueprint §7.2, §11.

### 6.10 Reaffirmed, Not Newly Decided

The following are already settled and are **restated only to prevent their being re-opened during implementation**:

- **PostgreSQL is the durable event store. `LISTEN/NOTIFY` is a wake-up mechanism and nothing else** (ADR-002). No message broker is introduced.
- **The `NOTIFY` payload is a thin envelope** — event id, aggregate type, aggregate id — never a domain object, bounded well inside the 8,000-byte limit (Blueprint §14 item 3).
- **Neither table carries an optimistic-lock version column.** A row that is never updated cannot lose an update race (ADR-005 5.6, Blueprint §7.1 item 8).
- **Neither repository exposes an update or a delete.** Append-only is enforced by construction (ADR-005 5.4, 5.7, 5.8) — with the same recorded limitation, that code holding a raw session could still bypass it.
- **Both repositories return domain objects, never ORM rows** (ADR-005 5.11), and **translate infrastructure failures** at the boundary (ADR-005 5.12).
- **Both tables carry persistence metadata timestamps** that no mapper reads and no query orders or filters by (ADR-005 5.9). [6.1](#61-total-ordering-by-database-generated-sequence) supplies the ordering key precisely so this prohibition is not quietly broken by the one layer most tempted to break it.
- **Checkpoint 5 owns both tables, both models, both migrations, and both repositories** (ADR-005 5.13).

## Consequences

### Positive

- **ADR-002's "wake-up only" claim becomes structurally true rather than aspirational.** [6.1](#61-total-ordering-by-database-generated-sequence) and [6.6](#66-subscribers-resume-by-sequence-position-held-in-memory) supply the mechanism that makes a missed notification recoverable, and [6.2](#62-the-notification-is-emitted-inside-the-committing-transaction) removes the window in which one is missed at all.
- **The Blueprint §7.2 invariant acquires the table it depends on.** A rejected transition has a durable, structured place to land before the Checkpoint 6 runner needs it.
- **Two Blueprint gaps are closed rather than absorbed**: nothing previously established event order, and nothing previously designed the recovery the §13 test was to verify.
- **The enforcement history is queryable in typed columns** ([6.3](#63-the-transition-audit-records-both-outcomes)) and does not depend on the payload schema this ADR defers.
- **The event vocabulary cannot drift from the schema** ([6.4](#64-a-closed-thirteen-entry-event-vocabulary)), by the same generated-constraint mechanism as every other vocabulary in the system.
- **The layer boundaries of §2.2 survive the event layer intact** ([6.9](#69-the-bus-receives-a-session-the-kernel-owns-the-call)); no dependency is inverted to make notification convenient.

### Trade-offs

- **A `pg_notify()` failure now rolls back the transition it accompanied** (§6.2). Accepted: an unobservable committed transition is worse than a visible retryable failure.
- **Successful transitions write two rows** (§6.3). Deliberate duplication; the two tables answer different questions.
- **The payload has no schema** (§6.5). Producers can drift until a later checkpoint constrains them.
- **Subscriber positions do not survive a process restart** (§6.6). Events are never lost, but universal observation is not guaranteed. **Recorded as a limitation, not claimed as enforcement.**
- **Staging an event and emitting its notification are two separate calls** (§6.9). Not enforced by construction; a required check at Checkpoint 6.
- **Checkpoint 5 delivers no observable behaviour.** Nothing writes an event during a real transition until Checkpoint 6. Its correctness is established entirely by tests, exactly as Checkpoint 4's was.
- **The producer of events does not exist yet.** §6.9 assigns the call to a Kernel that arrives next checkpoint, so Checkpoint 5's integration tests stand in as the caller.

## Questions Not Decided In This Record

These are surfaced by ADR-006 and are **not** resolved by it.

1. **Per-event-type payload schemas.** Newly deferred by [6.5](#65-strict-envelope-unconstrained-payload). **Owed to Checkpoint 6 or later**, once the Kernel and the API establish what consumers require. Recorded as an outstanding design task, not an architectural question.
2. **Durable subscriber positions and cross-restart delivery.** Newly deferred by [6.6](#66-subscribers-resume-by-sequence-position-held-in-memory). Foundation v1 guarantees durability of events, **not** universal observation across a subscriber restart.
3. **The authoritative / current QA-result selection mechanism.** Carried forward unchanged from [ADR-004](ADR-004.md) 4.15, [ADR-005](ADR-005.md) 5.9, and Blueprint §14 item 18. [6.1](#61-total-ordering-by-database-generated-sequence) **adds no mechanism for it**: `sequence_number` orders appends to one table and is not a QA-result selector. **Must be designed before Checkpoint 6.**
4. **The definition of "implementation task", the Feature-level mandatory evidence set, and the Reviewer assignment and routing model.** All three remain `BLOCKED_CONDITIONS` on the Checkpoint 6 critical path (ADR-004 4.11, 4.13; ADR-005 *Questions Not Decided* 3). **Checkpoint 5 adds no column, table, or index for any of them.**
5. **The Feature-level consequence of Feature Plan supersession.** Carried forward unchanged from [ADR-003](ADR-003.md) 3.13 and Blueprint §14 item 9. **Not touched by this ADR.**
6. **`FRONTEND` and `QA` mandatory System Evidence standards, and deterministic `DB_VERIFICATION` applicability.** Carried forward unchanged from [ADR-004](ADR-004.md) 4.9 and Blueprint §14 items 12 and 13.
7. **The Coordinator lifecycle, the Domain Registry, and Builder-approval registration.** Deferred capabilities **D-2** and **D-3**, carried forward unchanged from [ADR-003](ADR-003.md) 3.10 and Blueprint §14 item 7.

## Amendment — Checkpoint 5 Implementation Ruling (2026-09-04)

One Builder ruling made during Checkpoint 5 implementation, recorded here. **§6.1 through §6.10 are unchanged.**

### 6.11 The Event Vocabulary Belongs To The Domain Layer

**Decision.** `EventType`, `TransitionOutcome`, `OSEvent`, and `TransitionAuditRecord` are defined in **`domain/`**, not in `events/`.

`events/` retains what is genuinely infrastructure: the notification envelope, the channel, the emitter, and the subscriber.

| | |
| :--- | :--- |
| **Existing architectural requirement** | `events` depends on `domain` and `storage`; `storage` depends on `domain` (Blueprint §2.2). **A shared vocabulary that two sibling layers both consume belongs to `domain`** — the ruling ADR-004 4.7 already made for `TransitionCondition`, so that `state` could declare conditions and `rules` evaluate them without `rules` depending on `state`. |
| **Clarification** | Blueprint §11 places the event types in `events/types.py` and the event repository in `storage/repositories/`. The repository, its mapper, and the Unit of Work all consume those types, so that layout requires `storage` to import `events` while §2.2 has `events` importing `storage`. **The two placements cannot both hold.** Moving the vocabulary to `domain` resolves the cycle without amending §2.2 and without relocating the repository. |
| **Explicit deferral** | None. |

**Rationale.** `FeatureCreated`, `TaskAssigned`, and `ReviewCompleted` are business vocabulary, not persistence mechanics; the domain layer is where the architecture already keeps such vocabulary. The alternatives were worse: relocating the repositories into `events` would remove the `uow.events` and `uow.transition_audit` bindings [6.9](#69-the-bus-receives-a-session-the-kernel-owns-the-call) and Blueprint §7.2 both assume, and reversing §2.2's declared direction would amend a layering rule to accommodate a file path — while `events/listener.py`, which reads the backlog [6.6](#66-subscribers-resume-by-sequence-position-held-in-memory) requires, naturally wants to import `storage` anyway.

**This is a placement ruling, not a modelling one.** No field, value, or invariant recorded in §6.1–§6.10 changes. `sequence_number` is carried on the domain object as an optional field: it is unset before the append and populated on read, because [6.1](#61-total-ordering-by-database-generated-sequence) makes it `GENERATED ALWAYS` and the application therefore cannot supply it. **It is not persistence metadata** in the ADR-005 5.9 sense — it is the ordering authority and the subscriber resume token — and the 5.9 prohibition on `row_created_at` / `row_updated_at` is untouched.

**Aggregate and entity type remain unconstrained text.** [6.4](#64-a-closed-thirteen-entry-event-vocabulary) closed the *event type* vocabulary and nothing more. No `AggregateType` enumeration is invented here, because the Foundation v1 scope boundary admits no new vocabulary beyond what the architecture already records.

**Affects.** Blueprint §2.2 (confirmed, not amended), §11.
