# ADR-004: Rule Engine Foundation & Checkpoint 3 Scope

## Status

**Accepted — 2026-08-25. Amended 2026-08-29** — see [Amendment](#amendment--checkpoint-3-audit-rulings-2026-08-29).

Records the proposed Rule & Policy Engine architecture and the scope of Checkpoint 3, prepared following the Checkpoint 3 planning review. §4.14–§4.16 were added on 2026-08-29 by Builder ruling following the Checkpoint 3 implementation audit; §4.1–§4.13 stand unchanged.

This ADR is an implementation-foundation and clarification record for the Rule Engine. **It does not replace, restate, or redesign the architecture**, and it supersedes no prior record.

---

## Context

Design Sessions 001–009 froze the architecture. [ADR-001](ADR-001.md) established independent verification. [ADR-002](ADR-002.md) established the technology foundation and the principle that complexity must be earned. [ADR-003](ADR-003.md) resolved the domain-model and lifecycle ambiguities discovered during Checkpoint 2.

Checkpoint 2 implemented the pure domain layer (`domain/`) and the deterministic lifecycle state machines (`state/`). In doing so it declared — but deliberately did not evaluate — a vocabulary of **named OS validation requirements**: `TransitionCondition`, transcribed from Implementation Blueprint §5.1 and §5.2. Every `TransitionDefinition` already carries the `required_conditions` that govern its edge. The declaring module records the intent explicitly: "This checkpoint declares them; the Rule & Policy Engine (Checkpoint 3) evaluates them."

**Checkpoint 3 is the checkpoint that turns those declarations into executable, deterministic rules.**

Two questions had to be answered before any rule was written:

1. **What is the shape of the mechanism?** A rule engine is a load-bearing architectural component. Getting its contract wrong is expensive and hard to reverse, because every rule written against it must be rewritten.
2. **How many rules should Checkpoint 3 write?** The condition vocabulary contains 31 entries. Writing all of them against an unproven engine would pay the cost of a design error 31 times over.

The planning review considered two options: implement the full computable rule set in Checkpoint 3, or **build the generic engine first and prove it against a small number of real OS rules**. The Builder selected the second.

This ADR records that ruling and the architecture it fixes.

## Decisions

Each decision separates three things explicitly, following the frame established by [ADR-003](ADR-003.md):

- **Existing architectural requirement** — already stated in Design Sessions 001–009, ADR-001, ADR-002, ADR-003, or the Blueprint. Not decided here.
- **Clarification** — what this ADR resolves.
- **Explicit deferral** — what Foundation v1 will *not* implement, and what remains owed.

### 4.1 Generic Rule Engine With Explicit, Strongly Typed Python Rules

**Decision.** The OS provides a **generic, reusable rule execution engine**. Individual rules are **explicit, strongly typed Python implementations** of a single abstract `Rule` contract.

The following are **prohibited** as the rule authoring mechanism:

- a JSON rule DSL
- a YAML rule DSL
- any configuration-driven rule language
- an arbitrary expression evaluator
- LLM-based rule evaluation

Extensibility lives at the **engine boundary** — adding a rule class — never in an invented rule programming language.

| | |
| :--- | :--- |
| **Existing architectural requirement** | The domain model, lifecycle state machines, and transition rules must remain **directly owned and enforced by AI Engineering OS** (ADR-002, *Workflow Engine*). The OS is deterministic: agents may declare work ready, but only the OS determines whether objective transition criteria are met (Design Session 009). Provider independence — no AI SDK in OS core (Blueprint §9.1). |
| **Clarification** | The rule layer's authoring mechanism is typed Python, and the engine is a reusable execution mechanism rather than an interpreter. |
| **Explicit deferral** | None. |

**Rationale.** A rule DSL is a programming language, and a programming language is a system that must itself be specified, versioned, tested, and secured. ADR-002's "Complexity Must Be Earned" forbids introducing one before a demonstrated requirement exists. An expression evaluator would additionally let rule content arrive at runtime, placing enforcement logic outside the reviewed, version-controlled OS. LLM evaluation is excluded categorically: a non-deterministic evaluator cannot satisfy Design Session 009's requirement that enforcement be deterministic and reproducible, and ADR-001's independent-verification principle would be self-defeating if verification itself were a judgement call.

**Affects.** Blueprint §3 (`rules` module), §11, §15 Checkpoint 3.

### 4.2 Hybrid Evaluation

**Decision.** Rule evaluation is **hybrid**:

- Every rule whose declared prerequisites all held **is evaluated**, regardless of how many other rules have already failed. **Evaluation never stops at the first failure.**
- A rule is skipped **only** because a prerequisite it **explicitly declared** failed or was itself skipped. Skips cascade transitively.
- All meaningful failures are aggregated into one structured rejection.
- A prerequisite that was **not requested for the edge under evaluation does not cause a skip** — it did not fail; it was out of scope.

Prerequisite relationships are declared as an explicit edge set on each rule and validated at import time: every prerequisite must be registered and must sort **strictly earlier** than its dependent, which makes cycles structurally impossible and keeps evaluation single-pass.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Transition rejection explicitly explains *what conditions or evidence are missing* (Design Session 009). A rejected Worker submission "receives explicit missing list" (Design Session 009). Enforcement is deterministic at every workflow transition across all roles (Design Session 009). |
| **Clarification** | "Explicit missing list" is realised as aggregation across independent rules, and "meaningless" is always **declared** by the rule author rather than inferred by the engine. |
| **Explicit deferral** | None. |

**Rationale.** Stopping at the first failure would force a Worker through as many reject–resubmit cycles as it has defects, contradicting Design Session 009's explicit-missing-list model. Conversely, evaluating a rule whose premise has already collapsed produces a misleading failure that sends the Worker after the wrong problem. Requiring the dependency to be *declared* keeps the distinction reviewable rather than emergent.

**Affects.** Blueprint §8.2, §15 Checkpoint 3.

### 4.3 Deterministic, OS-Owned Rule Ordering

**Decision.** Evaluation order is **fixed and owned by the OS**:

| Stage | Category |
| :--- | :--- |
| 1 | Actor / Authority |
| 2 | State transition |
| 3 | Plan / Dependencies |
| 4 | Evidence |
| 5 | Acceptance |

Within a stage, order follows the rule's position in a module-level registry constant.

**Agents never choose rule ordering. Runtime configuration never reorders rules.** The engine exposes no method to add, remove, reorder, or prioritise a rule, and evaluation accepts only conditions and facts. Order is a property of the code, not of any input.

Stage 2 is declared and **empty in Foundation v1**: structural transition validity belongs to the state machine (§4.7). The slot is reserved so the approved order never has to be renumbered.

| | |
| :--- | :--- |
| **Existing architectural requirement** | The OS is the enforcement layer and owns deterministic lifecycle enforcement (Design Session 009). Behaviour must be deterministic and reproducible (ADR-002, *Testing Principles*). |
| **Clarification** | The fixed stage order, its ownership, and the structural absence of any reordering mechanism. |
| **Explicit deferral** | None. |

**Affects.** Blueprint §8, §15 Checkpoint 3.

### 4.4 Typed, Frozen RuleContext Of Caller-Supplied Facts

**Decision.** Rules receive all facts through a single **typed, frozen `RuleContext`** assembled by the caller.

A rule **must not** access:

- PostgreSQL, SQLAlchemy, or any database session
- repositories or any data-access abstraction
- the filesystem, the network, or any external service
- environment-dependent hidden state, a clock, or a random source

Every context field is a frozen domain model or a tuple of them, so the fact graph is immutable in depth, not merely at its surface.

Each rule **declares the facts it requires**. The engine verifies the context supplies them **before** calling the rule. A missing required fact raises a structured error naming the rule and the absent facts — the engine **fails closed** and never allows a rule to pass because a fact was not supplied.

The `RuleContext` carries only fields that at least one registered rule consumes. It contains **no clock**: no Foundation v1 rule needs the current time, and its absence is a determinism guarantee rather than an omission.

| | |
| :--- | :--- |
| **Existing architectural requirement** | `rules` depends on `domain` and must not own DB connection management (Blueprint §3). The domain layer is isolated from I/O so rules are testable in microseconds without database mocks (Blueprint §11, *Directory Rationale*). |
| **Clarification** | The mechanism is a typed frozen context prepared by the caller, with declared per-rule fact requirements and fail-closed handling of an incomplete context. |
| **Explicit deferral** | The **context loader** — the component that reads facts from persistence and assembles a `RuleContext` — is **not** part of Checkpoint 3. It belongs to the Checkpoint 6 Kernel and is built on Checkpoint 4 repositories. |

**Rationale.** A rule that can fetch its own facts can fetch different facts on two identical calls, destroying reproducibility. Fail-closed handling matters more than it may appear: a rule that silently passes because the caller forgot a fact is the exact failure mode ADR-001 exists to prevent — unverified work advancing because nobody checked.

**Affects.** Blueprint §3, §12.

### 4.5 Structured RuleResult With Stable Machine Identifiers

**Decision.** Every rule returns a **structured result**. Free-form error strings are **never** the machine contract.

A result carries:

| Element | Purpose |
| :--- | :--- |
| `rule_id` | Stable identifier of the rule that produced it |
| `status` | `PASSED` / `FAILED` / `SKIPPED` |
| `code` | **Stable machine-readable failure code** — the contract software depends on |
| `message` | Human-readable explanation of the problem |
| `details` | Typed, ordered structured data making the failure actionable |
| `skipped_because` | The prerequisite rule identifiers that caused a skip |

`rule_id` and `code` are **separate closed vocabularies**: one rule may emit several distinct codes. Both are pinned by test, so renaming either is a deliberate, reviewed breaking change rather than an accident.

Result well-formedness is invariant: `PASSED` carries no code; `FAILED` always carries one; `SKIPPED` carries no code and always names its cause. **A skip is never reported as a failure.**

An aggregate evaluation additionally reports **conditions that were requested but have no registered rule**, so a gap in enforcement is visible in the result rather than absent from it.

**`NOT_APPLICABLE` is deliberately not implemented in Foundation v1.** Because the engine evaluates only rules whose condition the state machine actually requested, no rule can be inapplicable to an evaluation it was selected for. A status with no producer is an unfalsifiable branch. It becomes earned the first time one condition maps to two conditionally exclusive rules; this record exists so its later addition is a deliberate act.

| | |
| :--- | :--- |
| **Existing architectural requirement** | The OS rejects invalid transitions, **explicitly explaining what conditions or evidence are missing** (Design Session 009). Rejections are durably preserved with structured `rejection_reasons` (Blueprint §4.1 #10, §8.2). QA Reports and Work Packages are **machine-first** (Design Sessions 004, 009). |
| **Clarification** | "Machine-first" applied to rule outcomes: the stable `code` is the software contract, the `message` explains, and `details` make the failure actionable. |
| **Explicit deferral** | The serialised wire format of a rejection over HTTP (Checkpoint 7) and its persisted audit shape (Checkpoints 4 / 5). |

**Affects.** Blueprint §4.1 #10, §8.2, §15 Checkpoints 3, 4, 5, 7.

### 4.6 Rules Are Pure Read-Only Evaluators

**Decision.** A rule **evaluates and returns**. It performs no other action.

A rule **must not**:

- mutate a Feature, Feature Plan, Task, Task Revision, Work Package, Evidence record, QA Report, or Decision
- write any database record
- write any audit record
- publish any event
- call any external service
- perform any hidden I/O

The Rule Engine **evaluates**. The Checkpoint 6 OS Kernel and transactional transition runner **mutate, audit, and publish**.

| | |
| :--- | :--- |
| **Existing architectural requirement** | `rules` must not own state mutation (Blueprint §3). A rejection never mutates anything: the Task is preserved in `IN_PROGRESS` and the rejection is durably recorded (Blueprint §8.2). `core` owns the transaction runner and enforcement pipeline (Blueprint §3, §7.2). |
| **Clarification** | Purity is an enforced structural property, verified by architectural test, not a convention. |
| **Explicit deferral** | None. |

**Rationale.** If a rule could mutate, a partially evaluated transition could leave the system in a state no transition defines — precisely the class of invalid state ADR-002's testing principles require to be unreachable through normal OS interfaces. Keeping mutation in exactly one place also keeps the transactional boundary in exactly one place.

**Affects.** Blueprint §3, §7.2, §8.

### 4.7 The Condition Vocabulary Moves To The Domain Layer

**Decision.** The `TransitionCondition` vocabulary of named OS validation requirements is **owned by the `domain` layer**.

The final dependency direction is:

```
              domain
             ↑      ↑
          state    rules
```

- **`domain`** owns the named condition vocabulary.
- **`state`** owns lifecycle graphs and transition definitions, and declares which conditions govern each edge.
- **`rules`** evaluates the conditions.
- **`rules` must not depend on `state`.**

Existing public re-exports are preserved so current imports continue to resolve. **No lifecycle behaviour changes** beyond the `ORIGINATING_PLAN_ACTIVE` declaration recorded in §4.8.

The separation of concerns is unchanged and remains three-way:

| Layer | Question it answers |
| :--- | :--- |
| `state` | *"Is this transition structurally defined, and may this initiator request it?"* |
| `rules` | *"Are the conditions this edge declares satisfied by these facts?"* |
| `core` (Checkpoint 6) | *"Atomically validate, mutate state, record audit, and publish event."* |

| | |
| :--- | :--- |
| **Existing architectural requirement** | Blueprint §3 declares `rules` depends on **`domain`** — not `state`. `state` depends on `domain`. |
| **Clarification** | Which layer owns the shared vocabulary. Checkpoint 2 placed it in `state` for proximity to the transition definitions that consume it; the Blueprint's declared dependency table requires it in `domain`. |
| **Explicit deferral** | None. |

**Rationale.** `TransitionCondition` is a vocabulary of *named requirements*, not state-machine mechanics. Both `state` and `rules` are consumers of it, answering different questions about the same named requirement. Placing shared vocabulary in the layer both depend on is the only arrangement that satisfies the Blueprint's dependency table without duplicating the vocabulary — and a duplicated vocabulary is a vocabulary that will drift.

**Affects.** Blueprint §3, §11. **Requires code change** — relocation only, with re-exports preserved.

### 4.8 Checkpoint 2 Revisit Performed In Full At Checkpoint 3 Start

**Decision.** The Checkpoint 2 revisit that [ADR-003](ADR-003.md) 3.11 and 3.12 left owed is performed **in full** at the start of Checkpoint 3, as Blueprint §15 schedules.

**QA defect scope (ADR-003 3.11).** `QADefect` gains `scope_task_id` and `scope_feature_id`. Permitted combinations:

| `scope_task_id` | `scope_feature_id` | Meaning |
| :--- | :--- | :--- |
| set | unset | Defect found against a Task; scope resolves `Defect -> Task -> Feature` |
| unset | set | No Task represents the affected capability; scope resolves `Defect -> Feature` |
| unset | unset | **Unresolved scope** — valid to record, blocks a QA Final Pass |
| set | set | **Rejected at construction** |

**Both-absent remains valid.** The OS derives scope from the relationship. **A QA-supplied boolean such as `in_scope = true` is never accepted as the authority**, and no such field exists on the model.

**Task plan linkage (ADR-003 3.12).** `Task.feature_plan_id` and `Task.plan_definition_key` are both **REQUIRED**. Every Task is traceable:

```
Task  ->  Feature Plan  ->  plan-local Task Definition
```

**Condition declaration (ADR-003 3.12).** `ORIGINATING_PLAN_ACTIVE` is added to the condition vocabulary and declared on **both** Task `-> READY` edges (`CREATED -> READY` and `PENDING_DEPENDENCIES -> READY`).

> **The `ORIGINATING_PLAN_ACTIVE` *rule* remains deferred** (§4.10). This revisit records domain facts and state declarations required by already-approved architectural decisions. **It is not permission to widen the Checkpoint 3 rule set.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | ADR-003 3.11 and 3.12 in full. Blueprint §15 Checkpoint 2 schedules this revisit "performed when Checkpoint 3 begins, not inside Checkpoint 2's completed record." Blueprint §15 Checkpoint 4 requires `tasks` to carry the originating-plan columns and QA defect rows the scope-association columns. |
| **Clarification** | Both revisits land together as one atomic event; the exact `QADefect` scope cardinality; both `Task` linkage fields are required rather than optional. |
| **Explicit deferral** | The **rule** evaluating `ORIGINATING_PLAN_ACTIVE`; ADR-003 3.12 states the gate is "enforced by the Checkpoint 6 transition runner." |

**Rationale.** Both-absent must remain constructible or ADR-003 3.11's "scope unresolved" path is unreachable and therefore untestable — the rule that must reject it could never be exercised. Making the `Task` linkage required follows Blueprint §4.1 #3, which omits the "(optional)" marker it applies elsewhere, and follows ADR-003 3.12's own reasoning that without the link the rule is unenforceable. Splitting the revisit across two checkpoints would leave the domain half-migrated across a Builder review boundary.

**Affects.** Blueprint §4.1 #3, §4.1 #7, §5.2, §15 Checkpoints 2, 3, 4. **Requires code change** — `domain/qa.py`, `domain/task.py`, the condition vocabulary, `state/task_sm.py`, and the corresponding Checkpoint 2 tests and fixtures.

### 4.9 Evidence Standards — Undefined Capabilities Fail Closed

**Decision.** Mandatory System Evidence requirements are keyed off **`Task.capability`** (ADR-003 3.7), never off `claim_type`.

**No mandatory System Evidence standard is invented for `FRONTEND` or `QA`.** Design Session 005 specifies the Backend Worker only.

For a capability with no approved standard, the evidence rule **fails closed** with the stable code `EVIDENCE_STANDARD_UNDEFINED`. **An undefined standard is never treated as "no evidence required."**

**`DB_VERIFICATION` is not part of the deterministic mandatory Checkpoint 3 evidence set.** Design Session 005's "Database verification (when applicable)" remains **unresolved engineering judgement** until a deterministic applicability rule is explicitly designed. **No applicability logic is invented here.**

The Foundation v1 evidence standard table is therefore:

| Capability | Mandatory System Evidence | Source |
| :--- | :--- | :--- |
| `BACKEND` | `GIT_DIFF`, `TEST_OUTPUT`, `API_RESPONSE` | Design Session 005, "Backend Worker / Required" |
| `FRONTEND` | **undefined** — fails closed | Open decision |
| `QA` | **undefined** — fails closed | Open decision |

The rule emits two distinct codes so a rejection never falsely blames the Worker for a gap in the OS: `MISSING_SYSTEM_EVIDENCE` (the Worker omitted required evidence) and `EVIDENCE_STANDARD_UNDEFINED` (the OS has not ruled the standard).

| | |
| :--- | :--- |
| **Existing architectural requirement** | Evidence requirements are defined by the OS; Workers never decide the minimum; **every Worker type follows predefined Evidence Standards** (Design Session 005). Backend required evidence: API response, test execution, git diff, database verification *when applicable* (Design Session 005). Stage 1 verifies required Evidence exists; Stage 2 is Reviewer judgement (Design Session 005). Evidence rules are keyed by capability (ADR-003 3.7). |
| **Clarification** | The behaviour when a capability's standard has not been ruled: fail closed, with a distinct code separating "standard undefined" from "evidence missing". `DB_VERIFICATION`'s conditionality is judgement, so it sits outside the deterministic minimum. |
| **Explicit deferral** | **The `FRONTEND` and `QA` mandatory System Evidence standards remain an explicit open decision.** A deterministic applicability rule for `DB_VERIFICATION` likewise remains undesigned. |

**Rationale.** Failing open would let a Frontend or QA submission pass the OS's Stage 1 evidence gate with no evidence at all — Design Session 005's "Workers may never provide less than the required minimum" silently reduced to no minimum. Failing closed makes the gap visible and blocking rather than invisible and permissive. Encoding "when applicable" as a rule would require the OS to make an engineering judgement Design Session 005 assigns to the Reviewer.

**Affects.** Blueprint §4.1 #5, §5.2, §14, §15 Checkpoint 3.

### 4.10 Checkpoint 3 Rule Scope — Six Representative Rules

**Decision.** Checkpoint 3 builds the **generic Rule Engine foundation** and implements exactly **six representative real OS rules**:

| Rule | Category | Condition | Edge |
| :--- | :--- | :--- | :--- |
| `worker_capability_matches` | Authority | `WORKER_CAPABILITY_MATCHES` | Task `READY -> ASSIGNED` |
| `dependencies_accepted` | Plan / dependency | `DEPENDENCIES_ACCEPTED` | Task `CREATED` / `PENDING_DEPENDENCIES -> READY` |
| `system_evidence_required` | Evidence | `MANDATORY_SYSTEM_EVIDENCE_ATTACHED` | Task `IN_PROGRESS -> SUBMITTED` |
| `all_tasks_accepted` | Acceptance | `ALL_TASKS_ACCEPTED` | Feature `IN_VALIDATION -> ACCEPTED` |
| `qa_final_pass_recorded` | Acceptance | `QA_FINAL_PASS_RECORDED` | Feature `IN_VALIDATION -> ACCEPTED` |
| `qa_in_scope_zero_defects` | Acceptance | `ZERO_UNRESOLVED_IN_SCOPE_DEFECTS` | Feature `IN_VALIDATION -> ACCEPTED` |

`qa_in_scope_zero_defects` declares `qa_final_pass_recorded` as its prerequisite. The other five are independent.

These six are **all four rules Blueprint §15 names for Checkpoint 3** (`AuthorityRule`, `SystemEvidenceRule`, `SequentialDependencyRule`, `QAInScopeZeroDefectRule`) plus the two acceptance rules that make hybrid evaluation demonstrable against real conditions rather than only against test doubles.

`qa_in_scope_zero_defects` implements ADR-003 3.11 exactly: it resolves each defect via `Defect -> Task -> Feature` or `Defect -> Feature`, counts only unresolved defects resolving to the Feature under acceptance, **never reads a QA-supplied scope flag**, and rejects a QA Final Pass carrying any scope-unresolved defect, **naming the defect** in the rejection. A defect resolving to a different Feature is permanently recorded and does not block this Feature.

**No other rule is implemented in Checkpoint 3.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | Blueprint §15 Checkpoint 3 names four rules and marks the `QAInScopeZeroDefectRule` precondition **CLEARED** by ADR-003 3.11. Complexity must be earned (ADR-002). |
| **Clarification** | Checkpoint 3's deliverable is the **engine architecture, proven against real OS conditions** — not the complete rule library. |
| **Explicit deferral** | Every other computable rule (§4.11). |

**Rationale.** The engine is the expensive, hard-to-reverse decision; the rules are cheap, linear, and independently reviewable. Proving the engine against six rules that span four categories, four evaluation stages, three lifecycle edges, two entities, and five distinct fact shapes — including the hardest rule the architecture currently supports — surfaces a design error while six rules would need rewriting rather than twenty-three.

**Affects.** Blueprint §15 Checkpoint 3.

### 4.11 Rule Expansion Boundary — Four-Way Condition Classification

**Decision.** Remaining rules are **never silently implemented**. Every entry in the condition vocabulary is classified into exactly one of four registry constants, and the classification is enforced by test:

| Classification | Meaning |
| :--- | :--- |
| **Implemented** | A registered rule evaluates it today |
| **`PENDING_RULE_EXPANSION`** | Deterministically computable against the current domain model; **not yet written**, deferred by scope decision alone |
| **`SATISFIED_BY_DOMAIN_INVARIANT`** | Structurally guaranteed by domain-model construction; a rule could never fail, so enforcement is discharged by pinning the guaranteeing validator rather than by writing an unfalsifiable rule |
| **`BLOCKED_CONDITIONS`** | Cannot be written without a Builder ruling or later-checkpoint machinery |

**Invariant.** The four sets **partition** the vocabulary — union complete, pairwise disjoint. No condition can be silently unenforced, and no rule may introduce a condition the architecture never declared.

A condition in `PENDING_RULE_EXPANSION` is a **scope decision**. A condition in `BLOCKED_CONDITIONS` is an **owed decision**. A condition in `SATISFIED_BY_DOMAIN_INVARIANT` is **already enforced, elsewhere**. Collapsing any two would let an unanswered architectural question hide inside a backlog, or force writing vacuous rules that only appear to enforce something.

**Classification as of Checkpoint 3.**

*Implemented (6):* `WORKER_CAPABILITY_MATCHES`, `DEPENDENCIES_ACCEPTED`, `MANDATORY_SYSTEM_EVIDENCE_ATTACHED`, `ALL_TASKS_ACCEPTED`, `QA_FINAL_PASS_RECORDED`, `ZERO_UNRESOLVED_IN_SCOPE_DEFECTS`.

*`PENDING_RULE_EXPANSION` (17):* `WORKER_IS_ACTIVE`, `REQUESTER_IS_ASSIGNED_WORKER`, `TASK_HAS_DEPENDENCIES`, **`ORIGINATING_PLAN_ACTIVE`**, `FEATURE_PLAN_ATTACHED`, `PLAN_HAS_TASK_DEFINITIONS`, `PLAN_IS_READY`, `WORK_PACKAGE_PRESENT`, `CLAIMS_DEFINED`, `VERIFICATION_GUIDE_PRESENT`, `REVIEW_DECISION_APPROVED`, `REVIEW_DECISION_CHANGES_REQUESTED`, `QA_REPORT_PASSED`, `TEST_EXECUTION_EVIDENCE_PRESENT`, `QA_REPORT_FAILED`, `INCREMENTED_REVISION_CREATED`, `QA_DEFECT_FINDINGS_RECORDED`.

*`SATISFIED_BY_DOMAIN_INVARIANT` (4):*

| Condition | Guaranteeing invariant |
| :--- | :--- |
| `PLAN_DEPENDENCIES_VALID` | `FeaturePlan` validates key uniqueness, dependency resolvability, and acyclicity at construction |
| `REVIEW_NOTES_PRESENT` | `ReviewDecision.notes` is mandatory non-empty text |
| `REVIEW_FEEDBACK_PRESENT` | Same field, same guarantee |
| `DEFECTS_DOCUMENTED` | `QAReport` requires a `FAILED` report to carry at least one defect; `QADefect` requires non-empty title, severity, and priority |

*`BLOCKED_CONDITIONS` (4):*

| Condition | Blocker | Unblocked by |
| :--- | :--- | :--- |
| `TASKS_INSTANTIATED` | Plan activation *performs* the instantiation (ADR-003 3.12); evaluating it before the runner acts is meaningless | Checkpoint 6 machinery |
| `ALL_IMPLEMENTATION_TASKS_ACCEPTED` | "Implementation task" is undefined across Design Sessions 001–009, ADR-003, and the Blueprint | Builder ruling |
| `MANDATORY_EVIDENCE_PRESENT` | No Feature-level required evidence set exists; Design Session 005's standards are per-Worker-type | Builder ruling |
| `REVIEWER_ASSIGNED` | **No domain concept exists** — `Task` carries no reviewer and there is no routing model | Builder ruling + Checkpoint 6 |

| | |
| :--- | :--- |
| **Existing architectural requirement** | Items marked UNRESOLVED or DEFERRED **must not be silently decided during implementation** (Blueprint §14.1). Every deferral is named, justified, and given a gating condition (ADR-003, *Consequences*). |
| **Clarification** | The mechanism by which that discipline is made machine-checkable rather than documentary. |
| **Explicit deferral** | None. |

**Affects.** Blueprint §14.1, §15.

### 4.12 Checkpoint 6 Safety Gate

**Decision.** The Checkpoint 6 OS Kernel **must not become operational against Foundation v1 while any required Foundation v1 transition condition lacks enforcement.**

```
Required Foundation v1 transition conditions
              ↓
   every required condition is either
   implemented by a Rule, or satisfied
   by a proven domain invariant
              ↓
        CP6 may proceed
```

Formally:

> `FOUNDATION_V1_REQUIRED_CONDITIONS` is a subset of (*implemented* union `SATISFIED_BY_DOMAIN_INVARIANT`)

Capabilities intentionally **outside** Foundation v1 are **not** required to be implemented merely because they exist in the global condition vocabulary.

**The governing invariant:**

> **No Foundation v1-required condition may be silently unenforced when the Kernel goes live.**

| | |
| :--- | :--- |
| **Existing architectural requirement** | The OS is the enforcement layer; mandatory rules are enforced deterministically at **every** workflow transition across all roles (Design Session 009). Agents may declare work ready, but only the OS determines whether objective transition criteria are met (Design Session 009). |
| **Clarification** | Checkpoint 3's narrowed scope leaves real requirements unenforced. This gate converts that from an untracked debt into a blocking precondition on the checkpoint where it would first cause harm. |
| **Explicit deferral** | None. |

**Rationale.** Narrowing Checkpoint 3 is safe **only because nothing calls the engine yet** — there is no Kernel until Checkpoint 6 and no control plane until Checkpoint 7. The moment the Kernel is wired in, an unimplemented required rule becomes a silently unenforced OS guarantee, which is the failure mode ADR-001 and Design Session 009 exist to prevent. Placing the gate at Checkpoint 6 puts it exactly where the risk materialises.

**Affects.** Blueprint §14, §15 Checkpoint 6.

### 4.13 Foundation v1 Required Conditions Derived From The Vertical Slice

**Decision.** `FOUNDATION_V1_REQUIRED_CONDITIONS` is **derived from the `TransitionCondition` entries attached to the transitions the approved Foundation v1 vertical slice (Blueprint §10.2) actually walks.** No separate, arbitrary checklist is invented.

The derivation:

| Slice step | Transition | Required conditions |
| :--- | :--- | :--- |
| 4 | Feature `DRAFT -> PLANNED` | `FEATURE_PLAN_ATTACHED`, `PLAN_HAS_TASK_DEFINITIONS` |
| 4 | Feature `PLANNED -> IN_PROGRESS` | `PLAN_IS_READY`, `TASKS_INSTANTIATED`, `PLAN_DEPENDENCIES_VALID` |
| 4 | Feature Plan `DRAFT -> READY -> ACTIVE` | *(no conditions declared)* |
| 4 | Task `CREATED -> READY` | `DEPENDENCIES_ACCEPTED`, `ORIGINATING_PLAN_ACTIVE` |

| 5 | Task `ASSIGNED -> IN_PROGRESS` | `REQUESTER_IS_ASSIGNED_WORKER` |
| 6, 7 | Task `IN_PROGRESS -> SUBMITTED` | `WORK_PACKAGE_PRESENT`, `CLAIMS_DEFINED`, `MANDATORY_SYSTEM_EVIDENCE_ATTACHED`, `VERIFICATION_GUIDE_PRESENT` |
| 8 | Task `SUBMITTED -> IN_REVIEW` | `REVIEWER_ASSIGNED` |
| 8 | Task `IN_REVIEW -> IN_QA` | `REVIEW_DECISION_APPROVED`, `REVIEW_NOTES_PRESENT` |

**Result: 24 of the 31 vocabulary entries are Foundation v1-required.**

The seven **not** required are the rework and multi-task edges the slice does not walk: `TASK_HAS_DEPENDENCIES`, `QA_DEFECT_FINDINGS_RECORDED`, `REVIEW_DECISION_CHANGES_REQUESTED`, `REVIEW_FEEDBACK_PRESENT`, `QA_REPORT_FAILED`, `DEFECTS_DOCUMENTED`, `INCREMENTED_REVISION_CREATED`. They remain part of the architecture and are not withdrawn; they simply do not gate Checkpoint 6.

**Gate status at Checkpoint 3 completion.** Of the 24 required conditions, 6 are implemented and 2 (`PLAN_DEPENDENCIES_VALID`, `REVIEW_NOTES_PRESENT`) are satisfied by domain invariant — **8 covered, 16 outstanding** (12 in `PENDING_RULE_EXPANSION`, 4 in `BLOCKED_CONDITIONS`). **The gate is therefore expected to fail at the end of Checkpoint 3, by design.**

**Consequence.** All four `BLOCKED_CONDITIONS` are Foundation v1-required. **Three Builder rulings** — the definition of "implementation task", the Feature-level mandatory evidence set, and the Reviewer assignment model — are therefore on the **critical path to Checkpoint 6**, not in a backlog.

| | |
| :--- | :--- |
| **Existing architectural requirement** | The first vertical slice exists to prove the OS workflow, deterministic rules, state tracking, and transition enforcement (Blueprint §10.1). The complete 11-step lifecycle is the Foundation v1 acceptance test (Blueprint §12, §15 Checkpoint 8). |
| **Clarification** | The required-condition set is *derived* from the slice rather than authored separately, so it cannot drift from the workflow it protects. |
| **Explicit deferral** | None. If the slice is ever extended, the required set is re-derived rather than edited by hand. |

## Amendment — Checkpoint 3 Audit Rulings (2026-08-29)

The Checkpoint 3 implementation audit surfaced three questions that §4.1–§4.13 did not settle. The Builder ruled on all three. **These rulings add to this record; they supersede nothing in §4.1–§4.13.**

---

### 4.14 Different Feature Is Out Of Scope — ADR-003 3.11 Contradiction Resolved

**Decision.** A defect whose scope association resolves to a **different Feature** is **out of scope for the Feature currently being accepted and does not block it.**

> Feature A = Login, Feature B = Payments. A defect associated with Feature B, evaluated while accepting Feature A, is a **known out-of-scope defect**. It is permanently recorded and does not block Feature A.

**Only genuinely unresolved scope blocks acceptance** — an association that is absent, or one that resolves to no entity.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Feature Acceptance requires zero unresolved **in-scope** defects; a capability outside the recorded scope is never silently treated as a defect (Design Session 009). |
| **Clarification** | [ADR-003 3.11](ADR-003.md#311-qa-defect-scope--verified-structural-association-never-a-declared-boolean) contained an internal contradiction: its *Unresolvable scope* paragraph classified a different-Feature association as **unresolved**, while its *Out-of-scope defects* paragraph classified the same association as **non-blocking**. This ADR's §4.10 had already followed the second reading. The Builder resolves the contradiction in favour of the **out-of-scope, non-blocking** reading. ADR-003 3.11 is amended accordingly. |
| **Explicit deferral** | None. The rest of the defect model is unchanged. |

**Rationale.** Treating another Feature's defect as a blocker would make every Feature's acceptance hostage to unrelated work, which is the opposite of Design Session 009's scope boundary. Recording it permanently preserves the other half: nothing is silently discarded.

**Affects.** ADR-003 3.11, Blueprint §4.1 #7, §5.1. **Requires code change** — none; the Checkpoint 3 implementation already followed §4.10.

---

### 4.15 QA History Is Audit History — The Authoritative QA-Result Mechanism Remains OPEN

**Decision.** The OS **must not treat every historical QA Report as a live acceptance blocker** — and that guarantee is delivered by **the context loader supplying only the authoritative facts**, never by a rule policing what it was handed.

Historical QA Reports are **immutable audit history**. A `QAReport` is frozen and has no update path, so an `OPEN` defect written into a superseded report stays `OPEN` in that record permanently. Feeding all of them to the acceptance rule would make any Feature that ever failed QA **permanently unacceptable**, rendering Design Session 009's `IN_VALIDATION -> IN_PROGRESS -> ... -> ACCEPTED` rework loop unreachable. The fix belongs where the facts are chosen, not where they are evaluated.

**The mechanism that identifies the authoritative / current QA result is NOT decided here and remains OPEN.** Checkpoint 3 invents none. Specifically it introduces **no** recency ordering, sequence number, timestamp comparison, "latest" marker, `current_report_id`, QA session identity, or persistence query, and **no additional `RuleContext` fact**.

**The boundary.** Selecting the authoritative QA result and evaluating it are two different concerns owned by two different components:

```
Future OS Kernel / context loader        →  selects the authoritative QA result
              ↓
          RuleContext                    →  carries the selected facts
              ↓
          Rule Engine                    →  evaluates the supplied facts
```

`qa_in_scope_zero_defects` owns **only** the second concern. It evaluates the QA Reports it is given and **takes no view on how many there are.** Selection is the caller's responsibility, per §4.4's rule that the context is *assembled by the caller*.

**A rule must not police the shape of its own fact set.** Repeat QA is architecturally normal: `QAReport.task_revision_id` scopes a report to a Task Revision, and the Blueprint §5.1 `IN_VALIDATION -> IN_PROGRESS` rework loop produces more of them. No approved record limits a Feature to one QA Report. A rule that rejected a Feature merely because several reports were supplied would be inventing QA workflow semantics it does not own — the negative half of a selection mechanism this ADR expressly defers — and would reject the documented rework path on facts that state nothing is wrong. Where facts are genuinely inadequate the approved channel is the **engine's** `RuleContextIncompleteError` (§4.4), not a rule verdict, and where a condition cannot be evaluated at all the approved channel is the §4.11 classification.

**The consequence is recorded rather than guarded against.** If a caller supplies superseded reports, their unresolved defects are evaluated as supplied. Preventing that is the loader's responsibility when it is designed; it is not something the rule may pre-empt by refusing to evaluate.

| | |
| :--- | :--- |
| **Existing architectural requirement** | Feature Acceptance requires zero unresolved in-scope defects (Design Session 009). Complete planning and validation history is preserved (Design Session 009). Append-only history is never rewritten (Blueprint §7.1). |
| **Clarification** | Immutable QA history is not a standing veto. Selecting the authoritative QA result is a **context-assembly** concern owned by the Checkpoint 6 loader; evaluating it is a **rule** concern. Neither component performs the other's job. |
| **Explicit deferral** | **The authoritative / current QA-result selection mechanism. It must be designed before Checkpoint 6**, because the Checkpoint 6 Kernel is what will assemble the `RuleContext` and therefore decide which QA Reports a rule sees. |

**Known consequence, accepted deliberately.** Until the authoritative-result mechanism exists, the correctness of this rule's verdict depends entirely on the caller supplying the right reports. Checkpoint 3 therefore proves the ADR-003 3.11 **derivation**, not the end-to-end acceptance guarantee. **This is a recorded limitation, not a claim of enforcement.**

**Affects.** Blueprint §4.1 #7, §5.1, §14, §15 Checkpoints 3 and 6. **Requires code change** — `rules/acceptance.py` (evaluate supplied reports; no cardinality judgement).

---

### 4.16 Dangling Feature References Are Out Of Checkpoint 3 Scope — The Seven-Fact Context Is Unchanged

**Decision.** **No `known_feature_ids` fact is added to `RuleContext`.** The seven approved facts of §4.4 remain exactly as approved.

**Consequence, stated plainly:** Checkpoint 3 **cannot** distinguish

- a defect associated with an existing **different** Feature, from
- a defect associated with a **nonexistent** Feature identifier.

Both are treated as out of scope under §4.14. **Checkpoint 3 does not claim to validate dangling Feature references, and no fake lookup is invented to imply that it does.**

A dangling **Task** reference *is* detected, because `feature_tasks` and `referenced_tasks` let the OS check that reference against supplied facts. The asymmetry is a direct consequence of the approved fact set, not an oversight.

| | |
| :--- | :--- |
| **Existing architectural requirement** | The `RuleContext` carries only fields that at least one registered rule consumes, and rules obtain facts without obtaining data access (§4.4). |
| **Clarification** | Referential validation of a Feature association is a **capability limitation** of Foundation v1 Checkpoint 3, recorded rather than worked around. |
| **Explicit deferral** | **Dangling Feature-reference detection must be addressed when the persistence and context-loader layer is designed** (Checkpoints 4 / 6), which is the first point at which the OS can establish whether a Feature identifier exists. |

**Rationale.** Adding a fact to make one rule stricter would put the fact graph ahead of the architecture that justifies it, and inventing a lookup inside a rule would breach §4.4's prohibition on rules fetching their own facts. Recording the limitation keeps it visible; papering over it would not.

**Affects.** Blueprint §4.1 #7, §11, §14, §15 Checkpoints 3, 4, 6.

## Consequences

### Positive

- The Rule Engine's contract is proven against real OS conditions **before** the rule library is written, so a design error costs six rewrites rather than twenty-three.
- Rule expansion becomes **bounded and mechanical**: one rule class, one identifier, its codes, one registry entry, and — where needed — one context field. **No engine change.**
- Enforcement gaps are **machine-visible**. The four-way classification partitions the vocabulary, and the engine reports requested conditions that have no rule.
- "Not written yet", "cannot be written", and "already enforced elsewhere" are structurally distinguishable, so an unanswered architectural question cannot hide in a backlog.
- Database independence is an **enforced structural property**, verified by import analysis and runtime I/O audit, not a convention.
- Every Task is traceable to its originating plan and definition key, so planning history is complete and the future authorization gate is computable (§4.8).
- A defect's acceptance impact is a **verified relationship**, never a self-declared boolean (§4.8).
- The layering conflict between Blueprint §3 and the Checkpoint 2 code is resolved rather than absorbed (§4.7).
- The Checkpoint 6 required-condition set is derived from the vertical slice, so it cannot drift from the workflow it exists to protect (§4.13).

### Trade-offs

- **Foundation v1 requirements are knowingly unenforced between Checkpoint 3 and the rule-expansion work.** Most notably: an **inactive or nonexistent Worker** may be assigned a Task; a **submission with no Work Package** is not gated; and a Task may reach `READY` under a non-`ACTIVE` plan. This is accepted deliberately because nothing calls the engine until Checkpoint 6, and it is bounded by the §4.12 gate.
- **Checkpoint 6 acquires a hard precondition** that did not previously exist, and three Builder rulings are on its critical path (§4.13).
- **`FRONTEND` and `QA` capabilities cannot pass the evidence gate at all** until their standards are ruled (§4.9). With the Foundation v1 vertical slice using a backend Worker this has no practical effect, but it is a real blocking gap.
- **Four conditions will never have rules** because domain validators already guarantee them (§4.11). The Blueprint's condition list and the implemented rule set will therefore never be identical; the classification keeps the difference visible.
- **Making `Task.feature_plan_id` and `plan_definition_key` required** invalidates every existing Task construction site in the Checkpoint 2 tests and fixtures. The change is mechanical but not free.
- **`ORIGINATING_PLAN_ACTIVE` is declared without its rule**, so a declared condition sits unenforced from Checkpoint 3 until Checkpoint 6, reported by the engine as unevaluated on every `-> READY` evaluation.

### Implementation impact

| Decision | Impact |
| :--- | :--- |
| 4.1–4.6, 4.10, 4.11 | New `rules/` package: engine, contract, context, results, codes, registry, and four category modules |
| 4.7 | Condition vocabulary relocated to `domain`; `state` imports it; public re-exports preserved. **Relocation only — no behavioural change** |
| 4.8 | `domain/qa.py`, `domain/task.py`, the condition vocabulary, `state/task_sm.py`, plus the Checkpoint 2 fixtures and tests that construct `Task` and `QADefect` |
| 4.9 | Capability-to-evidence table inside the evidence rule; `EVIDENCE_STANDARD_UNDEFINED` code |
| 4.12, 4.13 | New Blueprint §15 Checkpoint 6 precondition; derived required-condition set and gate test in the rule registry suite |

New structured error types (rule definition, incomplete context, rules rejected) join the existing `DomainError` hierarchy, following the precedent that the state layer's `StateMachineDefinitionError` already lives in `domain/errors.py`.

The Implementation Blueprint requires updates in §3, §4.1 (#3, #7), §5.2, §11, §14, and §15 (Checkpoints 2, 3, 4, 6).

**No new runtime dependency.** No persistence, event, HTTP, or Kernel work is performed at Checkpoint 3.

## Foundation v1 Scope Boundary

Confirmed **in scope** for Foundation v1 Checkpoint 3, as clarified by this ADR:

- A generic Rule Engine with explicit, strongly typed Python rules.
- Hybrid evaluation with deterministic, OS-owned stage ordering and declared prerequisites.
- A typed, frozen `RuleContext` of caller-supplied facts, with fail-closed handling of an incomplete context.
- Structured `RuleResult` with stable rule and code identifiers and typed details.
- Pure, read-only rules with no persistence, audit, event, or external I/O.
- The six representative rules of §4.10.
- QA defect scope as a verified structural association, with unresolved scope representable.
- Required Task-to-Plan-to-Definition linkage.
- The `ORIGINATING_PLAN_ACTIVE` **declaration**.
- The four-way condition classification and the derived Checkpoint 6 gate.

Confirmed **out of scope** for Foundation v1 Checkpoint 3:

- Any rule DSL, expression language, or LLM evaluation.
- `NOT_APPLICABLE` as a rule status.
- The remaining computable rules (`PENDING_RULE_EXPANSION`).
- The `ORIGINATING_PLAN_ACTIVE` **rule** — Checkpoint 6.
- Any context loader, repository, or fact-fetching protocol — Checkpoints 4 / 6.
- Any Work Package lifecycle rule — precluded by ADR-003 3.5.
- Mandatory evidence standards for `FRONTEND` and `QA`; `DB_VERIFICATION` as a mandatory item.
- Escalation blocking and the `BLOCKED` state (**D-1**); the Coordinator lifecycle, Domain Registry, and Builder-approval registration (**D-2**, **D-3**); Feature Plan supersession from `DRAFT` or `READY` (**D-4**); a severity/priority taxonomy (**D-5**); a Task stop/abandon terminal state and any persisted disposition record (**D-6**).

**Nothing in this ADR converts a deferred capability into a Foundation v1 requirement.**
